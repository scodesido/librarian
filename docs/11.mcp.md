# 11. MCP: exposing retrieval to external LLM clients

This document describes the MCP (Model Context Protocol) server that
exposes the retrieval pipeline (`09.retrieval.md`) to external LLM
clients — primarily claude.ai — alongside the internal HTTP endpoints
the FE already uses. The server lives in `api/mcp.py` and is mounted
on the FastAPI app at `/mcp`.

## Goal and shape

claude.ai (and other MCP clients) can connect to a "remote MCP server"
and call tools registered on it. We want to expose `/data/query`'s
agent-driven retrieval as one such tool, so a chat with claude.ai can
search the user's own library without going through our FE.

The exposed surface is intentionally tiny: one tool, `query_library`,
taking the same two arguments as `POST /data/query` (`question` plus an
optional `search_terms` override). Mirroring the internal endpoint's
shape was a deliberate choice — every additional MCP-specific concept
is another thing the calling LLM has to learn from the tool
description, and another thing that can drift from how the FE uses the
library.

Transport: **Streamable HTTP** (the MCP spec's successor to the older
SSE transport). claude.ai uses this for remote MCP servers; FastMCP
mounts cleanly into FastAPI through a single ASGI sub-app.

## One retrieval driver, three callers

The most important architectural choice here is that there is **one**
implementation of the retrieval pipeline — `service/retrieval/run.py`'s
`run_retrieval` — used by all three callers:

- `POST /data/query` (JSON): calls `run_retrieval` with `emit=None`, maps
  `RetrievalResult` onto `QueryResponse`.
- `POST /data/query/stream` (SSE): calls `run_retrieval` from a
  background task, with `emit` pushing onto an `asyncio.Queue`; a
  heartbeat-aware loop in the SSE generator drains the queue and writes
  `text/event-stream` frames.
- `query_library` MCP tool: calls `run_retrieval` directly, with `emit`
  translating each `QueryEvent` into a `Context.info(...)` log
  notification on the active MCP session. Returns the final
  `RetrievalResult`'s projection (`MCPQueryResult`).

`run_retrieval` itself does not own a database connection — the caller
passes one. The JSON endpoint reuses the request-scoped connection
(`DbConnection` dep); the SSE generator and the MCP tool acquire a
fresh one from the pool, because they keep working after the
originating request handler returns.

The shared `emit` shape (`Callable[[QueryEvent], Awaitable[None]] |
None`) is the seam between the agent's internal events and whatever
the caller wants to do with them. The agent itself (and its tools) only
ever calls `deps.emit`; it has no awareness of SSE or MCP.

## Progress via `Context.report_progress`

The MCP `Context` exposes both `info(...)`-style log notifications and
`report_progress(progress, total, message)`. We surface every event
through `report_progress` rather than `info`, because in practice
claude.ai shows log notifications only in a dev panel, whereas the
`message` argument of a progress notification lands directly on the
tool card as the "what's happening right now" line under the spinner.

The `progress` and `total` numbers do flow through too, but they're
secondary — the *message* is what actually communicates state. The
descent budget is a ceiling, not a runway: the agent often answers
well before exhausting it, so the fraction shown is at best a "we're
at step k of up to budget" indicator, not a faithful percentage. We
let the message carry the truth and treat the bar as decoration.

The mapping is:

- `TermsEvent` → `progress=0, total=None, message="Searched for:
  '<terms>' (extracted from question | as provided)."`. Total is
  unknown at this point (the budget is only finalised inside the
  agent's `setup_query`), so clients render message-only.
- `ExpandEvent` → `progress=step, total=budget, message="Step
  k/budget: expanded N node(s) [ids...]."`. This is where the bar
  starts moving.
- `FetchEvent` → `progress=last_step, total=last_budget,
  message="Peeked at N blob(s) [ids...]."`. Inherits the last
  step/budget from the most recent expand — fetch doesn't count
  against the budget, so the bar stays put while the message updates.
- `DoneEvent` → not emitted as a progress notification; its payload
  becomes the tool's structured return value.
- `ErrorEvent` → never reached on the success path; on failure the
  exception is raised as a tool error and the calling LLM sees the
  message directly.

`report_progress` is a silent no-op if the client didn't send a
`progressToken` with the call. claude.ai does. Other clients that
don't will see only the final tool result — no progress mid-flight,
but no hard failure either.

## Tool result shape

`MCPQueryResult` is a strict subset of the internal `RetrievalResult`:

- `rationale: str` — the retrieval agent's short note explaining its
  selection. Kept because the calling LLM benefits from knowing *why*
  these blobs were chosen, not just *what* they contain.
- `effective_search_terms: str` — what was actually embedded for
  scoring. Useful when the calling LLM omitted `search_terms` and we
  ran the pre-flight extractor; the LLM can see whether the distilled
  string captured what it meant.
- `blobs: list[BlobResult]` — same shape the JSON / SSE endpoints
  return: source file path, byte/page range, structured abstract,
  plaintext contents.

We deliberately drop `visited_node_ids` and `steps`. They're useful
internal debugging signal but they're noise to the calling LLM: knowing
the agent visited node 47 doesn't help the LLM answer the user's
question, and exposing internal node IDs to an external system risks
making them part of an implicit contract.

## Auth: none for now

MCP today only standardises OAuth, and claude.ai only supports
OAuth-based MCPs for browsing the catalog. Setting up a per-user OAuth
flow for a single-user dogfood deployment is more work than is
warranted right now, so the `/mcp` endpoint is **unauthenticated** and
runs every call as the operator-pinned user in `MCPSettings.user_id`
(env `LIBRARIAN__MCP__USER_ID`).

If the setting is `None`, the tool fails at call time with a clear
"MCP user_id is not configured" message — the server still starts
(retrieval still works through the FE-facing endpoints), but the MCP
tool is unusable until a user_id is configured.

The operational expectation is that `/mcp` is reached only through a
private reverse proxy (see README "Remote MCP via ssh -R + nginx"); it
should not be exposed to the open internet without auth. A future
revision will replace the pinned user_id with a real auth layer (the
TODO comment in `MCPSettings.user_id` calls this out).

## Mounting under FastAPI

FastMCP exposes two ways to embed a Streamable-HTTP transport into an
existing ASGI app:

1. `mcp.streamable_http_app()` returns a Starlette sub-app with a single
   inner `Route` at `streamable_http_path` (default `/mcp`). Mounting
   it under FastAPI at `/mcp` would require setting
   `streamable_http_path="/"` to avoid `/mcp/mcp`, and even then
   FastAPI's mount path stripping doesn't cleanly match the empty
   sub-path.
2. `StreamableHTTPASGIApp(session_manager)` is the bare ASGI handler
   the Starlette wrapper delegates to. It doesn't inspect the request
   path; it just dispatches on method (POST / GET / DELETE).

We use option 2. `api/mcp.build_asgi()`:

- Calls `mcp.streamable_http_app()` once for its side effect (lazily
  initialising `mcp._session_manager`); discards the returned Starlette
  app.
- Wraps the now-created session manager in a `StreamableHTTPASGIApp`
  and returns it.

`api/app.py` then registers that ASGI as two Starlette `Route`s — one
at `/mcp` and one at `/mcp/` — rather than `app.mount("/mcp", ...)`.
Mount internally uses a `/mcp/{path:path}` regex, which means a bare
`/mcp` (no trailing slash) falls through to Starlette's
`redirect_slashes` logic and gets a 307 to `/mcp/`. That redirect
chain is brittle in two specific ways that bit us when first wiring
this up to claude.ai:

1. The `Location` header is built from `scope["path"]`, which only
   contains a reverse-proxy prefix if uvicorn was started with
   `--root-path`. With the proxy stripping the prefix and `root_path`
   not set, the redirect points at the wrong absolute path on the
   public host.
2. claude.ai's remote-MCP onboarding normalises the URL (strips a
   trailing slash) before testing the connection. So even if the user
   enters `/mcp/` in the UI, the first request goes to `/mcp` and
   takes the redirect. And on some HTTP clients, the redirected POST
   loses its body (the spec preserves it for 307, but in practice the
   chain isn't always faithful).

Two exact-match Routes at `/mcp` and `/mcp/` both pointing at the
same ASGI app sidestep both problems — neither URL ever produces a
redirect, and the deployment stops being sensitive to `root_path`.

The session manager's own lifecycle (`session_manager.run()`) is run
from the FastAPI lifespan, after the DB pool and HTTP client are
attached:

```python
async with attach_db_connection_pool(app), attach_http_client(app):
    attach_deps(app.state.db_connection_pool, app.state.http_client)
    try:
        async with mcp.session_manager.run():
            yield
    finally:
        detach_deps()
```

`attach_deps` populates a module-level `mcp_deps` singleton that the
tool function reads. A module-level mutable is not ideal, but it's the
pragmatic answer to the fact that an MCP tool running inside the
mounted sub-app has no direct handle on the parent FastAPI app's
`state` — and any of the alternatives (passing through `ctx.fastmcp`,
spinning a second pool through a FastMCP-owned lifespan, monkey-
patching the session_manager) are worse.

## Stateless mode

The server is created with `stateless_http=True`. The Streamable-HTTP
spec has a notion of multi-request sessions (with a session id header
and an `initialize → tools/call → ...` lifecycle), but we don't keep
any per-session state on the server side: each retrieval is
self-contained. Stateless mode spins up a fresh transport per request,
which matches reality and avoids the cost of session tracking.

## What's intentionally out of scope (for now)

- **OAuth / per-call auth.** See "Auth: none for now" above. The
  expected next step.
- **Multiple tools.** Today only `query_library`. A natural extension
  is a `peek_blob(blob_id)` tool the calling LLM could use to re-fetch
  a single blob without running a new retrieval, but no concrete
  motivation yet.
- **Resource exposure.** MCP supports "resources" (read-only handles
  on documents the LLM can pull into context). We could expose tree
  nodes or whole files as resources; we don't, because the retrieval
  flow is what the LLM actually needs and resources would invite the
  LLM to pull whole files into context unprompted.
- **Streaming the agent's tokens.** Same caveat as the SSE endpoint —
  we emit tool-call-granularity progress, not LLM tokens.
- **Server-side caching of results across MCP calls.** Each call is a
  fresh retrieval. The Anthropic prompt cache on the inner agent's
  instructions still applies on the retrieval side.
