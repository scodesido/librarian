# 04. The abstraction tree

This document describes the layered DAG that Librarian builds on top of a
user's blobs, the three workers that maintain it, and the rules they
follow to stay coherent without explicit coordination. It builds on
`03.data_files.md` (the file/blob layer underneath).

## Goal

Each blob carries one chunk of a source file. To answer questions across
a user's library we want more than blob-level retrieval: we want a tree
of progressively higher-level abstractions, where each non-leaf node is a
synthetic summary clustered from a group of children below it. Retrieval
walks down that tree from the most general node to the most specific
relevant ones.

The data model has to support:

- Many small per-blob facts (the leaves), produced by parsing source
  files with an LLM.
- Many internal nodes built by clustering nodes one level down, each one
  carrying its own LLM-generated summary.
- Multiple kinds of vector encodings per node, so retrieval can match on
  different facets of the same abstract (summary, topics, running
  summary, ...).
- A pipeline that runs in the background, can be parallelised where it
  makes sense, and is safe to interrupt at any point.

## Blobs and nodes are different things

`data_blobs` and `tree_nodes` look 1:1 for leaves but they exist as
separate tables. The reason is lifecycle, not column count. Chunking and
abstracting are different expensive operations:

- Re-chunking requires re-reading the source file. Expensive in I/O and
  in upstream API quota.
- Re-abstracting requires running the LLM with a (possibly new) prompt,
  but the chunk boundaries don't need to change.

Keeping them in two tables makes "wipe abstracts and recompute" a single
`DELETE FROM tree_nodes` while the blobs survive. It also matches the
service split below: the blob_builder writes blobs and leaf nodes; later
workers only touch nodes and edges. Clean tables match clean services.

## A layered DAG, not a strict tree

`tree_nodes` carries an explicit `height`. Height-0 nodes are leaves
(one per blob, enforced by `UNIQUE (blob_id)` plus a CHECK that ties leaf
existence to a non-null blob and `state = 'READY'`). Internal nodes have
`height > 0` and no blob.

`tree_edges` records parent→child relationships with a single invariant
enforced by trigger: `parent.height = child.height + 1`. With heights
fixed at row creation, that constraint alone is enough to make the
structure a layered DAG with no cycles by construction. We allow
multiple parents per child — the clustering algorithm may produce
overlapping clusters at higher levels, and forcing a strict tree would
constrain it for no schema benefit.

When an edge is deleted, an `AFTER DELETE` trigger checks whether the
parent has any remaining outgoing edges; if not, it deletes the parent
node. The parent's deletion cascades to *its* incoming edges, which fire
the same trigger one level up, so a single leaf removal collapses any
ancestor subtree whose only path to a leaf went through that leaf. This
falls out without a recursive CTE — Postgres's per-row trigger semantics
do the work.

## Wipe-on-reset is the answer to "new files arrived"

KNN clustering is a global operation: the right partition of N+5 leaves
is genuinely different from the right partition of N. Trying to graft new
leaves onto an existing clustering produces a hybrid tree of two epochs,
which is worse than starting over.

So when Worker 1 picks up a new file (any time `tree_state.level >= 1`
and a PENDING file appears), it issues:

```sql
DELETE FROM tree_nodes WHERE user_id = $1 AND height > 0;
UPDATE tree_state SET level = 0 WHERE user_id = $1;
```

The cascade chain handles cleanup: edges fall via FK CASCADE; leaves are
left untouched (height = 0). The system is back in "leaves phase" and
will rebuild upward once the new leaves are in.

The cost is throwing away CPU spent on the previous build. We accept
that: the design optimises for tree quality, not for incremental
amortisation. Sync is a deliberate user action, not a continuous stream.

## Three workers, one gate

Three background services maintain the tree. They share no state besides
the database.

- **Worker 1 — `blob_builder`.** Picks the next PENDING file. In one
  transaction at the end: writes its `data_blobs` rows, writes the
  matching height-0 `tree_nodes` (state READY), writes their
  `node_embeddings`, marks the file READY. Per-file processing makes the
  running-summary abstract field workable: each blob's running summary
  is computed from the previous one in source order, all within the same
  worker run.
- **Worker 2 — `parent_creator`.** Builds one full layer of parent nodes
  at a time. Per-level KNN is global, so this worker is *not* internally
  parallelisable; only one instance per (user, level) at a time.
- **Worker 3 — `abstract_writer`.** Takes a height > 0 node in PENDING
  state, computes its abstract from its children's abstracts, writes
  embeddings, marks it READY. Fully parallelisable.

They coordinate through one row per user in `tree_state`:

```
level = 0       leaves phase: Worker 1 may run; Workers 2 and 3 sleep.
level = K >= 1  Worker 2 may build height-K parents; Worker 3 may fill
                pending nodes at any height; Worker 1 may run too,
                resetting level to 0 if it finds new PENDING files.
```

Transitions:

- Worker 1 bumps `level` from 0 to 1 once there are no PENDING/PROCESSING
  files left (the leaves are settled).
- Worker 1 resets `level` to 0 (and wipes h>0 nodes) the moment it picks
  up a new PENDING file from a level >= 1 state.
- Worker 2 bumps `level` from K to K+1 at the end of the build, in the
  same transaction that inserts the level's nodes and edges.

Worker 2's gate to actually run, given `tree_state.level = K`:

1. No height > 0 nodes at height K-1 are still PENDING/PROCESSING (i.e.,
   Worker 3 has caught up at the layer below).
2. There is more than one node at height K-1 (otherwise that layer
   already contains the root and we are done).

Worker 3's gate is purely local: pick any PENDING height > 0 node whose
children are all READY.

## Atoms, claims, crash recovery

Each worker's "atom" is the unit of work it commits or loses as a whole:

- Worker 1: one file. Too long for a single transaction (Drive download
  + LLM calls). Claim mechanism: `UPDATE data_files SET state =
  'PROCESSING' ... WHERE id IN (SELECT ... FROM data_files WHERE state =
  'PENDING' ... FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING ...`. Multiple
  workers naturally pick disjoint files. The actual processing happens
  outside the transaction; the final write of blobs + leaf nodes +
  embeddings + state=READY is one transaction.
- Worker 2: one full level for one user. Claim mechanism: `SELECT FROM
  tree_state WHERE user_id = $1 FOR UPDATE`, held for the whole build.
  Concurrent Worker 2 instances for the same user serialise; for
  different users they run independently.
- Worker 3: one node. Claim mechanism mirrors Worker 1's: `UPDATE
  tree_nodes SET state = 'PROCESSING' ... FOR UPDATE SKIP LOCKED LIMIT
  1`. Single-node atoms keep crash blast radius minimal.

Crash recovery is implicit: if a worker dies mid-claim, the row stays in
PROCESSING with a stale `claimed_at`. A periodic sweeper (or a startup
hook on each worker) resets PROCESSING rows older than a configurable
timeout back to PENDING. No distributed lock manager, no heartbeats.

A FAILED state catches "we tried this and it definitively didn't work"
(e.g., LLM rejected the input, blob couldn't be parsed). FAILED files
don't gate Worker 1's "leaves are settled" check — they're terminal — so
the system can move on to building the tree without them.

## Embeddings live in their own table

`node_embeddings(node_id, field, model_id, embedding vector(1024))`
keys on the triple, not on node_id alone. This shape supports:

- **Multiple facets per node.** "summary", "topics", "running_summary"
  are distinct vectors over distinct text. Retrieval can target any of
  them, or combine them.
- **Multiple encoders per facet.** A new model_id can be rolled out
  alongside the previous one with no schema change. KNN queries
  specialise to one (field, model_id) pair via a WHERE filter; pgvector
  indexes can be partial-indexed per partition once query patterns
  stabilise.

Dimension is fixed at 1024, matching the planned encoder. Other models
that produce different dimensions would need either a new column or a
parallel table; this is a known constraint of pgvector.

The KNN index itself is intentionally not created in the migration. The
right choice (HNSW vs IVFFlat, distance metric, partial-by-field)
depends on query patterns we don't yet have. Adding an index later is a
single cheap migration.

## What's intentionally out of scope (for now)

- **The workers themselves.** Only the schema and the coordination
  contract are committed. The service implementations are the next step.
- **Cross-user trees.** Each user has their own tree. There is no global
  index; retrieval is per-user.
- **Incremental tree updates.** Wipe-on-reset is the only update path.
  If recompute cost becomes a problem, an epoch-based scheme (mark the
  current build "stale" and build a new one alongside, then atomic swap)
  is the natural next step — but it doubles storage during builds and
  isn't worth the complexity until we feel the pain.
- **The retrieval path.** Walking the tree to answer a query is a
  separate concern. The schema is shaped to make it efficient (heights,
  per-facet embeddings) but no retrieval endpoint exists yet.
