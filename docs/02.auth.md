# 02. Authentication

This document describes the authentication architecture: how a user proves
who they are, how the backend keeps that fact across requests, and how the
frontend cooperates with both. It assumes the API foundations described in
`01.base_api.md`.

## Goal

Librarian's first feature is browsing the user's Google Drive. So the
authentication system has two jobs:

1. **Identify the user** to our application (so we can attach data to a
   stable account).
2. **Hold a delegated authorization** to call Google APIs on the user's
   behalf, even when the user is not currently active in the browser.

Both jobs are served by a single Google OAuth 2.0 flow, with the results
split across two database tables: a session cookie tracks browser identity,
and a long-lived refresh token (encrypted at rest) backs server-side calls
to Google.

## Identity provider: Google OAuth 2.0

We use Google as the sole identity provider. Two reasons:

- The product is built around Google Drive. Any user we care about already
  has a Google account, and the same consent screen that signs them in also
  grants the Drive scopes we need.
- Outsourcing identity to Google removes a class of work we do not want
  (passwords, email verification, account recovery) and a class of risk we
  do not want to carry (credential storage).

The flow is the standard Authorization Code flow with `access_type=offline`
and `prompt=consent`, requesting `openid`, `userinfo.email`, and
`drive.readonly`. We force `consent` so that Google reliably returns a
refresh token on every login, including reconnects.

The OAuth endpoints live in `api/endpoints/oauth/google.py`. Helpers that
talk to Google's token and userinfo endpoints live in
`api/core/oauth/google/tokens.py`. Endpoint code orchestrates; helpers do
the HTTP. This split keeps the endpoint readable as a state machine.

## Two tables, two responsibilities

`auth_google` and `auth_sessions` exist as separate tables on purpose:

- `auth_google` is the **link between our user and their Google identity**.
  Keyed by `user_id`, with a unique `sub` (Google's stable subject ID), it
  stores the encrypted refresh token and the granted scopes. Its lifetime is
  "as long as the user is connected to Google". One row per user.
- `auth_sessions` is a **browser session**. Keyed by an opaque, randomly
  generated session id, it expires after a configurable TTL (default 1 day).
  A user can have many concurrent sessions (multiple devices) without
  re-running the OAuth flow.

`users` itself holds nothing Google-specific, leaving room for additional
identity providers later without restructuring.

Why split this way:

- The refresh token is sensitive and rarely needed (only when we call Google).
  It should not ride along with every authenticated request.
- Sessions need to be cheap to create, rotate, and revoke. Tying them to the
  refresh token would force us to re-authenticate the user every time we
  wanted to invalidate a device.
- Logging out should drop the session without dropping Google connectivity
  — the next login on the same browser should not require a fresh consent.

## Session model: opaque cookie, server-side state

Sessions are server-side. The cookie (`session_id`) carries an opaque random
identifier (`secrets.token_urlsafe(32)`), and the database holds the mapping
to a `user_id` plus an `expires_at` timestamp.

We chose this over JWT/stateless tokens because:

- We want logout and revocation to be immediate and cheap. With server-side
  sessions, deleting the row is sufficient. JWT revocation requires a
  blocklist, which is server-side state in disguise.
- Session payload is one integer (`user_id`); there is no measurable
  benefit to encoding it in the cookie itself.
- Expiry is enforced in the SQL query (`expires_at > now()`), which makes
  reasoning about it trivial.

The cookie is `HttpOnly`, `SameSite=Lax`, and `Secure` in any non-local
environment (controlled by `google_oauth.cookie_secure`). `Lax` is enough
for our cross-site needs because the only top-level navigation we depend on
is the OAuth callback, which is a `GET`. The session cookie is not exposed
to JavaScript, so XSS in the frontend cannot exfiltrate it directly.

## CSRF defense: state cookie

The OAuth callback is the one cross-site request we accept. We protect it
with the standard `state` parameter — a random value set as a short-lived
HttpOnly cookie on the `/login` redirect, read back on `/callback`, and
compared with `secrets.compare_digest`. The state cookie is deleted as soon
as the callback completes.

Authenticated API endpoints other than the callback only accept requests
that already carry our session cookie. Because the cookie is `SameSite=Lax`,
foreign sites cannot trigger an authenticated state-changing request from
the browser.

## Refresh tokens are encrypted at rest

Refresh tokens are long-lived bearer credentials for the user's Google
account. Even though they live behind database access controls, we encrypt
them at the application layer before storing them.

The implementation (`api/core/oauth/google/crypto.py`) wraps Fernet
(authenticated symmetric encryption from `cryptography`). The key comes from
settings as `SecretStr`, so it must be supplied per environment and is never
hardcoded. Decryption is exposed as a `refresh_token` property on
`AuthGoogleModel`, so call sites get a plaintext string only at the moment
they need to make a Google call.

This gives us:

- A meaningful blast-radius reduction if a database backup leaks: the
  refresh tokens are not directly usable.
- A single chokepoint to rotate the encryption key (re-encrypt offline,
  swap the setting, done) without touching SQL.

We deliberately do not store access tokens. They are short-lived and cheap
to refresh; persisting them would just expand the surface area for no gain.
Each call to a Google API goes through `refresh_access_token` to mint a
fresh access token and uses it within that one request.

## The dependency: `CurrentUser`

Endpoints that require authentication declare a `CurrentUser` parameter
(`api/core/auth/user.py`). The dependency reads the session cookie, resolves
it against `auth_sessions`, and returns the `user_id` — or raises a 401 if
the cookie is missing, unknown, or expired.

This is the only place the cookie name and session lookup live. Endpoints
do not see cookies, do not see the session table, and do not handle 401s
themselves. To make a route public, you simply omit the dependency.

## Frontend integration

The frontend treats authentication as a small state machine
(`frontend/src/auth/use-auth.ts`):

- On mount, fetch `GET /auth/me`.
- A `200` produces an `authenticated` state with the returned `Me` object.
- A `401` produces an `anonymous` state, which renders the login screen.
- The login button navigates the top frame to `GET /oauth/google/login`,
  which redirects to Google and back through `/callback`. The backend
  finishes by setting the session cookie and redirecting to a configured
  post-login URL (the frontend root).
- Logout posts to `/oauth/google/logout` and re-runs the `/auth/me` probe.

`fetch` requests go through a thin `api()` wrapper that hardcodes
`credentials: "include"` so cookies are sent on cross-origin requests. CORS
on the backend allows this because `allow_credentials=True` is set and the
frontend origin is in the allow-list (see `01.base_api.md`).

The frontend never sees the session token. It only ever observes
authenticated-or-not, which is exactly the information it needs to choose
between `LoginScreen` and `HomeScreen`.

## What's intentionally out of scope (for now)

- **Multiple identity providers.** The data model accommodates them
  (`auth_google` is one of potentially several `auth_*` tables), but no
  others are wired up yet.
- **Account merging.** A new Google `sub` always creates a new user. There
  is no "link this Google account to my existing user" flow.
- **Scope step-up.** We request all scopes upfront at first consent. If we
  later add features needing additional scopes, we will revisit this.
- **Refresh-token rotation alerts.** Google can revoke or rotate refresh
  tokens; we currently surface failures only at call time. A background
  health check is a candidate for later.
