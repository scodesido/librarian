# 06. tree_builder: ready blobs → balanced abstraction tree

This document describes the second of the three workers introduced in
`04.immutable_data_pipeline.md`. The `tree_builder`'s job is to take
ready files (those with a `data_blobs.is_final_blob = TRUE` row) and
weave their blobs into a per-user metric-space tree whose internal
nodes have valid centroids and bounded fan-out.

## Goal

After `blob_extractor` runs, a user's blobs are durable in
`data_blobs` but disconnected from any tree structure. `tree_builder`
incrementally:

1. Adds new blobs to the existing tree via a descent algorithm that
   prefers less-populated subtrees (so the tree stays roughly
   balanced).
2. Splits any node that grows past `max_children_per_node` (K),
   propagating splits upward and creating a new root one level higher
   when the old root itself splits.
3. Maintains `data_node_weights` rows — one per node, holding the
   subtree's centroid and total blob_count — which the descent and
   split steps both consume.

There is no "wipe and rebuild" path: the tree grows incrementally and
locally. The previous design's per-level KNN rebuilds are gone.

## Three operations, one priority order

Each worker iteration performs **exactly one operation** chosen by
strict priority:

1. **Backfill one missing weight.** Find a node lacking a
   `data_node_weights` row whose dependencies are satisfied (a
   height-0 node, or a height>0 node whose every child already has a
   weight). Compute centroid (L2-normalised mean for leaves; L2-
   normalised weighted mean of children's centroids for internal
   nodes) and blob_count, INSERT.
2. **Split one overfull node.** Find a node whose total child count
   (`data_node_edges` + `data_blob_edges` where it's the parent)
   exceeds K. Split it (algorithm below).
3. **Insert one ready file's blobs.** Find a file whose blob set is
   complete and which has at least one blob lacking a
   `data_blob_edges` row. Descend the tree once per blob, attaching
   each at its closest leaf.
4. If none of the above: sleep `poll_interval_seconds`.

After any productive iteration the worker immediately retries (no
sleep). So in practice a worker that finds N missing weights does N
fast successive iterations and lands in steady state quickly.

This per-operation granularity (instead of one giant
"backfill-all → insert → split-all" mega-iteration) is the design
choice that lets the per-user advisory lock be **transaction-scoped**
(`pg_advisory_xact_lock`). The lock auto-releases on commit, so no
operation can leak a lock onto a pooled connection. Concurrent
`tree_builder` workers for the same user serialise per-operation;
across users they run in parallel.

The priority order is the convergence guarantee:

- Weights first ⇒ descents always see well-defined centroids.
  (Insertions defensively raise `MissingCentroidError` if they ever
  see one missing, but in normal operation that path is unreachable.)
- Splits before inserts ⇒ new blobs land in a tree that's not in the
  middle of being restructured.
- Inserts ⇒ forward progress.

A worker that sees no work does not poll harder than
`poll_interval_seconds`; once work appears the loop drains it
without delay.

## The user lock

`pg_advisory_xact_lock(user_id)` is acquired immediately after the
worker identifies a user with pending work. This serialises all
tree-mutating operations for one user; without it a concurrent
worker could split a node our iteration is descending through, etc.
The lock is transaction-scoped, so the commit at the end of each
operation releases it automatically.

The lock is **not** held across operations within a single iteration
— each iteration is exactly one operation, one transaction. Two
consecutive iterations of the same worker re-acquire the lock from
scratch, which is fine because each operation is idempotent against
the current DB state. Other workers can interleave between
iterations; the algorithm converges regardless of interleaving order.

## Centroid math: unit-normalised aggregation

All centroids are stored unit-normalised (L2). Both the descent
algorithm and the split-assignment formula compute euclidean
distance, and unit-normalising the centroids keeps the geometry
well-conditioned.

- **Leaf weight** (height=0 node): centroid =
  `normalize(mean(child.embedding_with_file))`; blob_count = number
  of child blobs.
- **Internal weight** (height>0 node): centroid =
  `normalize(weighted_mean(child.centroid, weights=child.blob_count))`;
  blob_count = sum of child blob_counts.

Children's `embedding_with_file` is already unit-normalised by
`blob_extractor`; the choice to re-normalise after aggregation keeps
the recurrence consistent.

The blob_count at the root equals the user's total blob count by
construction. This invariant is not enforced by a trigger but falls
out of the recurrence.

## Descent: weighted-distance pick at each level

To insert a blob into the tree, the algorithm starts at the user's
root and walks down. At each height>0 node it picks the child whose
weighted distance is smallest:

```
weighted_distance(emb, child_centroid, child_blob_count, mean, alpha)
    = ||emb - child_centroid|| * (child_blob_count / mean) ** alpha
```

`mean` is the mean of the children's blob_counts at that level.
`alpha` defaults to 0.1: a child with twice the average blob_count
gets a ~7% distance penalty. The descent thus prefers less-populated
subtrees, which is the long-term mechanism that keeps the tree
roughly balanced even before splits fire.

The blob's representative vector is `embedding_with_file` (not the
raw `embedding_blob`). The file-aware variant biases blobs of the
same file toward the same subtree, which is what we want for
retrieval — a query that hits one blob of a document is likely to
benefit from neighbours in the same document.

When the descent reaches a height-0 node it stops and inserts a
`data_blob_edges (parent_node_id = leaf, child_blob_id = blob)`
row. The blob_edge's `AFTER INSERT` trigger then invalidates the
leaf's weight (deletes it), and the resulting `data_node_weights`
delete cascades upward by trigger. Next iterations rebuild what's
needed.

## Split: pick two seeds, balance-assign the rest

`max_children_per_node` (K, default 4) sets the fan-out cap. K must
be > 2 — a K=2 split produces 2 new nodes, so the children must
distribute strictly between them, and at K=2 the split couldn't
reduce the count below threshold and the tree would never settle.

Split sequence (one transaction):

1. Find the highest-height over-K node. `ORDER BY n.height DESC` —
   splits propagate upward as the new edges fire weight invalidation
   on the grandparent, and starting high avoids zigzagging the
   propagation.
2. List its children with representative vectors:
   - height=0 parent: children are blobs; representative =
     `embedding_with_file`; blob_count = 1.
   - height>0 parent: children are nodes; representative = centroid;
     blob_count from `data_node_weights`.
3. Pick the two children with the **furthest euclidean distance**
   between representatives as seeds. O(K²) over the children's
   vectors — K is small, so this is trivial.
4. Determine the grandparent G:
   - Non-root: G is the (single) parent of the over-K node. The
     algorithm only creates single-parent edges; multi-parent state
     is rejected with a `RuntimeError`. The schema allows
     multi-parent (UNIQUE is on `(parent_node_id, child_node_id)`,
     not on `child_node_id` alone), keeping the door open for a
     future overlapping-cluster mode without requiring a migration.
   - Root: create a new root one level higher (height = old.height
     + 1, is_root = TRUE). The old root will be deleted in step 7;
     the deferred root-uniqueness trigger then passes at commit
     because there's exactly one is_root row.
5. Create two new sibling nodes at the same height as the over-K
   node, and add edges G → new_a, G → new_b.
6. Greedy-assign children to seeds. Order: descending blob_count
   (largest mass placed first; smaller children fill the imbalance).
   For each child, compare weighted distance to seed_a's running
   centroid and seed_b's running centroid, with the imbalance penalty
   driven by each seed's running blob_count. Place the child under
   whichever seed wins. Create the matching `data_node_edges` (node
   child) or `data_blob_edges` (blob child).
7. Delete the over-K node. FK cascades remove its outgoing edges
   (to its old children — but those children now have new edges
   from new_a/new_b, so they're not orphaned) and its incoming edge
   from the old grandparent. Deferred orphan-collection runs at
   commit; the deleted node's old children are anchored to new_a /
   new_b, so nothing else collapses.

Weight/abstract invalidation triggers fire eagerly throughout: the
new edges in steps 5-6 invalidate any pre-existing weight on
new_a, new_b, G (none expected on the newly-created nodes;
G's gets reset if it had one). The next iterations of `tree_builder`
will backfill those weights bottom-up.

## Failure handling: per-worker exponential backoff

Same shape as `blob_extractor`: exceptions abort the iteration's
transaction (losing any in-flight work for that iteration only —
not for the file, since each operation is one tx) and trigger a
backoff sleep. The next iteration retries from current DB state.

A persistently-broken state (e.g. a malformed weight row) keeps
falling into the worker's backoff log. There is no failure table.

## Concurrency: pick a user, take its lock, work, repeat

`concurrent_workers` (default 1) is the number of `worker_loop`
copies in the process. Multiple workers can run, but for a single
user only one operation proceeds at a time (the advisory lock
serialises). Multi-user scaling is linear in the worker count up to
the connection pool's limit.

Worker iterations are short (one read query + one or two writes,
typically), so the connection pin overhead is negligible and the
default 10-connection pool comfortably handles the default
1-worker configuration.

## What's intentionally out of scope (for now)

- **Multi-parent / overlapping clusters.** The schema permits
  multi-parent edges but the algorithm always produces single-parent
  ones. A future "soft clustering" mode could add edges without
  changing the table shape; the split step's grandparent-lookup
  would need to grow a strategy beyond "single parent".
- **Cosine vs euclidean distance.** The current implementation uses
  euclidean. With centroids unit-normalised, cosine and euclidean
  are monotonically related; switching wouldn't change ranking.
- **Periodic global re-balance.** If the per-blob descent biases
  drift over time, a future maintenance pass could re-cluster a
  subtree. None of that is needed yet.
- **Eviction / pruning.** The tree only grows. Deleting a file
  cascades to its blobs and their `data_blob_edges`, which triggers
  deferred orphan-collection; the relevant subtree collapses
  naturally. No periodic GC is needed.
