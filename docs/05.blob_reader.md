# 05. blob_reader: from PENDING file to leaf nodes

This document describes the first of the three workers introduced in
`04.tree.md`: the `blob_reader`. Its job is to take a PENDING file row,
read the actual content from Drive, cut it into blobs, generate one
Abstract per blob, embed selected fields of each Abstract, and persist
the whole bundle as a height-0 tree node — all atomically per file.

## Goal

Sync produces `data_files` rows in PENDING with `path` and `type` set,
and nothing else. The blob_reader is what turns those rows into queryable
material:

```
data_files (PENDING)
   ↓ blob_reader
data_files (READY)
   + data_blobs
   + tree_nodes (height=0, READY)
   + node_embeddings
```

After blob_reader, every leaf the abstraction tree might want to cluster
exists in the database, with its abstract and its embeddings.

## Vendor neutrality through pydantic-ai

Both the LLM call (Abstract generation) and the embeddings call go
through `pydantic-ai`:

- **LLM:** `pydantic_ai.Agent(settings.llm_model, output_type=Abstract,
  instructions=...)`. The model string is `"<provider>:<model>"` —
  `"anthropic:claude-haiku-4-5"` by default. Switching to a different
  Claude model, or to OpenAI / Gemini / Bedrock, is a settings change
  with no code change.
- **Embeddings:** `pydantic_ai.Embedder(settings.embedding_model)`. The
  default is `"voyageai:voyage-4"` to match the 1024-dim
  `node_embeddings.embedding` column. Same provider-string convention.

Pydantic-AI exposes a typed `Abstract` directly (we don't parse JSON
ourselves — the agent's `output_type` does it), and the embedder returns
an `EmbeddingResult` with `.embeddings` indexable per input. The choice
of provider is something settings — and only settings — controls.

API keys are passed explicitly into the provider constructors from
`blob_reader.anthropic_api_key` / `blob_reader.voyage_api_key` rather
than being left to the SDKs to read from env. The reason is forward-
compatibility: when secrets get mounted as files (rather than env vars),
we want one well-known seam — the settings field — that the secrets
layer can target. Letting the SDKs read env directly would force the
secrets layer to materialise env vars, which is the wrong shape.

Today these settings load from `LIBRARIAN__BLOB_READER__ANTHROPIC_API_KEY`
and `LIBRARIAN__BLOB_READER__VOYAGE_API_KEY` via `pydantic-settings`'s env
source. Tomorrow they will load from a mounted secret file with no code
change — the settings shape is the same.

The model strings (`"anthropic:claude-haiku-4-5"`,
`"voyageai:voyage-4"`) still pick the provider, but provider construction
goes through `build_llm_model` / `build_embedder`, which dispatch on the
prefix and inject the explicit key. Adding a new provider is a new
branch in those helpers, not a settings shape change.

## PDF blobs: bytes, not text

Files of type PDF are sliced into N-page sub-PDFs (default N=10) using
`pypdf.PdfReader` + `PdfWriter`. Each sub-PDF is sent as a
`BinaryContent(media_type="application/pdf")` part of the agent prompt,
not as extracted text.

Why bytes:

- Charts, diagrams, layout-driven content (tables, equations) survive.
  These are exactly the things our `content_type` taxonomy cares about
  ("charts", "data") and that disappear under naïve text extraction.
- PDF parsing in code is full of edge cases (column order, scanned PDFs,
  embedded fonts). Punting that work to the LLM is more robust than
  building a heuristic pipeline ourselves.

The cost is more tokens per call. For 10-page PDFs and Haiku's pricing
this is acceptable; the chunk size is configurable
(`pages_per_blob`) for cases where it isn't.

`data_blobs.start` and `end` for PDFs are **1-indexed inclusive** page
numbers. A blob covering pages 1-10 has `(start=1, end=10)`. The
sub-PDF re-emitted by `PdfWriter` is what the LLM actually sees.

## TEXT blobs: word-bounded character ranges

For TEXT files, we tokenize on whitespace (`re.finditer(r'\S+', text)`),
group every N words (default 1500), and emit one blob per group.

`start` and `end` are **character offsets in the original file**, not
word indices: blob N's text is exactly `original_text[start:end]`. We
chunk by words because "10 pages of a PDF" is a unit that translates
naturally to "1500 words of plain text", but we record by chars because
that's what later retrieval needs to slice the original file.

## OTHER blobs: marked READY without blobs

Files of type OTHER (everything that isn't PDF or text/*) get
transitioned PENDING → READY without producing any blobs or nodes. The
sync phase already chose to record them; the processing phase
acknowledges they exist but does not analyse them. They contribute to
the user's "total files" count but not to the tree.

## Abstract: six fields, one anchored running summary

```python
class Abstract(BaseModel):
    summary: str             # ~100 words, configurable
    topics: list[str]        # ~5, configurable
    intended_audience: str
    content_type: list[str]  # essay, data, technical doc, law, charts, ...
    domains: list[str]       # prefer one for leaves
    running_summary: str     # ~80 words, configurable
```

Five of the six fields are blob-local: they describe just this chunk.
The sixth — `running_summary` — is the only place where one blob's
processing reaches across blobs. The contract:

- For the **first blob** of a file, the agent has no prior context. The
  prompt asks it to use the `running_summary` field to express what the
  whole document seems to be about, based on this blob alone.
- For **subsequent blobs**, the prompt includes the previous blob's
  `running_summary` and asks the agent to weave the new blob into it.
  The result is a chain of progressively-refined "what this document is
  about" snapshots, one per blob.

This chain is the reason blob_reader processes one file end-to-end
within a single worker run: parallelising blob-level work within a file
would break the chain. Files between users (and within a user) are
still independent and can be processed concurrently across workers.

## Embeddings: a configurable subset of fields, in one batched call

`embedded_fields` (default `["summary", "topics", "running_summary"]`)
chooses which Abstract fields get vectorised. List values are flattened
to comma-separated strings before embedding. All blobs × all fields for
a single file go through one `embedder.embed_documents(...)` call — one
network round-trip per file, regardless of blob count.

`intended_audience`, `content_type` and `domains` aren't embedded by
default because their values are categorical and short; they're more
useful as JSONB filters than as similarity anchors. The setting allows
adding them later.

The embeddings are stored in `node_embeddings(node_id, field, model_id,
embedding)`, with `model_id` taken from `settings.embedding_model`
verbatim — so a future migration to a different model rolls out as new
rows alongside the old ones, not replacements.

## Per-file atomicity

The whole pipeline for one file is structured as a long async sequence
followed by one short transaction:

1. (No transaction) Acquire short connection, look up `auth_google`.
2. (No transaction) Refresh access token, download Drive bytes, chunk,
   call the LLM N times (one per blob), call the embedder once. This is
   the slow part: it can take minutes; no DB connection is held.
3. (Single transaction) Insert all blobs, all leaf nodes, all
   embeddings; mark the file READY. If any insert fails, the whole batch
   rolls back and the worker treats the file as failed.

If the worker crashes during step 2, no DB writes happened. The file
stays in PROCESSING until the sweeper resets it back to PENDING; the
next claim re-does the work from scratch. There is no partial state to
clean up.

## Claim mechanism: one short SQL statement

Claims use the standard Postgres recipe:

```sql
UPDATE data_files SET state = 'PROCESSING'
WHERE file_id = (
    SELECT file_id FROM data_files
    WHERE state = 'PENDING'
    ORDER BY created_at
    LIMIT 1
    FOR UPDATE SKIP LOCKED
)
RETURNING ...
```

`FOR UPDATE SKIP LOCKED` makes N concurrent workers each pick a
different row with no coordination beyond Postgres's own row locks.
`ORDER BY created_at` gives oldest-first ordering, which keeps queue
latency bounded.

The update bumps the row's `updated_at` (via the existing trigger),
which doubles as the claim timestamp. The sweeper queries
`WHERE state = 'PROCESSING' AND updated_at < now() - $timeout` and
flips stale claims back to PENDING. No `claimed_at` column, no
`claimed_by`, no heartbeats — the existing `updated_at` carries enough
information.

## Failure handling: explicit FAILED state

Any exception from `process_file` lands the file in FAILED. This covers
upstream failures (Drive 404, OAuth refresh failed), LLM failures
(rate limit, malformed structured output), and our own bugs. FAILED is
a terminal state — the worker won't retry it on its own.

Re-trying a FAILED file is currently a manual operation (set state back
to PENDING). A future enhancement is per-file retry counts and
exponential backoff; the schema already supports it (just add
`retry_count INT` if needed). It's intentionally out of scope for now.

`FAILED` files don't gate the eventual "leaves are settled" check that
Worker 2 will look at — they're terminal, the system moves on without
them.

## Concurrency: many files, one file at a time per worker

`concurrent_workers` (default 1) is how many copies of `worker_loop`
run in one process. Each loop:

1. Claims one file.
2. Processes it end-to-end.
3. Goes back to step 1.

With `concurrent_workers > 1`, N files are in flight at once for the
same user (or across users). Increase this when LLM latency rather than
LLM rate-limit becomes the bottleneck. The connection pool's
`max_connections` (default 10) is the upper bound that matters; bump it
together with `concurrent_workers` if you push it high.

The sweeper runs as a single extra task alongside the worker loops,
checking on a cadence of `max(60s, claim_timeout / 4)`.

## What's intentionally out of scope (for now)

- **Workers 2 and 3.** This service only writes leaves. Higher-level
  parents and their abstracts are the next step (`tree_state`-driven
  builder + abstract writer).
- **Retry and backoff.** FAILED is terminal. Manual unsticking only.
- **Streaming downloads / partial PDFs.** Drive files are fetched
  whole. For very large PDFs this would matter; for the current
  workload it doesn't.
- **Custom prompts per content_type.** The Abstract agent's
  instructions are one fixed string. Specialising per detected type
  could improve quality but requires an extra LLM pass to classify
  first.
