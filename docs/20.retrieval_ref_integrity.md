# 20. Retrieval ref integrity

## The bug

The retrieval agent (`09.retrieval.md`) walks the tree by passing *refs* —
opaque-looking strings like `n:172` (node) or `b:455` (blob) — to its tools.
A real query exposed a failure: while exploring a topology paper, the
"Listed file fragments" step (`list_file_blobs`) came back with blobs from an
unrelated Swiss banking-law PDF. The agent, understandably, got confused.

The data was clean and the tool's query was correct: `list_file_blobs`
faithfully returned the blobs of whatever file the ref it was given resolved
to. The problem was the ref itself. At that point in the walk the agent had
only run `list_children` (returns nodes) and `node_detail` (returns prose) —
it had **never reached a single blob**, so it had no legitimate `b:` ref in
hand. It fabricated one: it reused the integer of the node it had just
inspected (`n:12`) as a blob ref (`b:12`).

That worked because the two failures compounded:

1. **Overlapping id spaces.** `node_id` and `blob_id` were independent
   per-table sequences, both starting at 1. So `12` was simultaneously a
   valid node id and a valid (different, unrelated) blob id. The instructions
   even warned the agent about this — a warning is not a guarantee.
2. **No provenance check.** The tools validated a ref's *format* (`b:` prefix)
   and *existence*, both of which a fabricated-but-real ref passes. Nothing
   checked whether the agent had actually been *shown* that ref.

## The fix: two independent layers

Neither layer alone is sufficient, and they fail closed in different ways, so
we apply both (defense in depth).

### Layer 1 — disjoint id space (DB)

A single sequence, `data_tree_element_id_seq`, now feeds both
`data_nodes.node_id` and `data_blobs.blob_id`. No integer is ever
simultaneously a valid node id and a valid blob id, so the *cross-kind*
collision is structurally impossible: `b:<a node id>` resolves to nothing and
the tool returns a corrective error instead of the wrong file.

This governs new inserts only, so it is fully effective on a *rebuilt* tree.
The per-blob-processing migration (`19.per_blob_processing.md`) already clears
`data_files` and forces a re-sync; once that rebuild runs, every id is drawn
from the shared sequence and the spaces are disjoint from then on. The old
per-table sequences are left in place (unused) so the change is cleanly
reversible.

What this layer does *not* stop: a fabricated ref of the *right* kind that
happens to name a real element the agent never reached, or an outright
hallucinated ref. That is Layer 2's job.

### Layer 2 — provenance gate (retrieval tools)

`QueryDeps` carries a `seen_refs` set. It is seeded with exactly the refs the
instructions seed exposes (the root and its immediate children — the only
refs the agent can legitimately use before its first descent), and grows as
the walk proceeds: `list_children` records the children it returns,
`list_file_blobs` records the file blobs it lists. Every tool calls
`ensure_refs_seen` on its inputs before touching the DB; a ref that was never
surfaced is refused with a `ModelRetry` that points the agent back at
`list_children`. The agent can therefore only act on refs it actually reached
by descent — fabrication of any kind becomes a corrective retry rather than a
silent wrong answer.

The `FinalAnswer` bypasses the tools, so it is the last fabrication surface.
`run_retrieval` drops any final `blob_ref` not in `seen_refs` (a legitimately
chosen blob was peeked and is therefore present), logging a warning rather
than failing the whole query — mirroring the defensive `cap_blob_ids` trim.

See `service/retrieval/provenance.py`, the guards in
`service/retrieval/tools/`, and the seeding in `run.setup_query`.
