# 03. Data files and sync

This document describes the first piece of the data layer: how Librarian
keeps a per-user inventory of the files it knows about, and how that
inventory is reconciled with the user's Google Drive. It builds on
`01.base_api.md` (folder/router conventions, `Table` pattern) and
`02.auth.md` (refresh-token flow into Drive).

## Goal

Eventually Librarian will run a custom RAG-like protocol over the user's
Drive contents. The first step toward that is to materialise, in our own
database, the set of files we will eventually process — without yet
fetching their contents. This separation matters because:

- Listing Drive is cheap and idempotent. Downloading and chunking is
  expensive and stateful. We want to be able to do the first repeatedly
  and the second exactly once per file.
- All later work (chunking, embedding, retrieval) operates against rows in
  our database, not Drive responses. Drive is the upstream truth for "what
  files exist"; our database is the truth for "what we've processed".

## Two tables: `data_files` and `data_blobs`

The data model has two tables:

- `data_files` — one row per file we know about. Holds the identity
  (`path`, `source`), the kind of content (`type`), and the processing
  state (`state`). Keyed by an internal `file_id` (BIGSERIAL) so the rest
  of the system never depends on Drive-specific identifiers.
- `data_blobs` — one row per processed chunk of a file. Holds an opaque
  `(start, end)` range whose meaning is type-dependent (page numbers for
  PDF, character offsets for TEXT). Cascade-deletes with its parent file.

Why the split:

- Files and blobs have different lifecycles. A file row is created the
  moment we discover it; blobs are created later, possibly multiple times,
  possibly never (for `OTHER` files). Putting them on the same row would
  conflate "we know this file exists" with "we've finished processing it".
- The same file may produce many blobs. A separate table is the natural
  shape for that 1:N relationship.
- Re-processing a file is "delete its blobs, then re-extract", which is a
  scoped operation that the cascade makes safe.

## `path` is whatever the source needs to retrieve the file

The `path` column is intentionally vague: it's the string the source
adapter needs to fetch the file. For `source = 'GDRIVE'` it is the Drive
file ID; for a future `source = 'S3'` it would be a bucket key, and so on.
This keeps the table source-agnostic at the schema level and pushes the
interpretation into the adapter that owns the source.

`UNIQUE (user_id, source, path)` is the natural identity of a file — the
same Drive ID for the same user is the same file, regardless of how it was
discovered. The unique constraint also enables the sync's `INSERT ... ON
CONFLICT DO NOTHING` upsert.

## Three types: PDF, TEXT, OTHER

Drive contains many mime types we don't (yet) want to extract from:
spreadsheets, images, Google-native documents, and so on. Two options for
handling them: filter them out at sync time, or keep them in the table
with an explicit `OTHER` marker.

We chose `OTHER` because:

- The set of "what we know exists in this Drive" is a useful answer in
  its own right (totals, % covered) and we don't want it skewed by an
  invisible filter.
- Adding support for a new mime type later then becomes "reclassify
  existing OTHER rows" rather than "rerun a sync that previously dropped
  them".
- Blob population is the gate. A file of type `OTHER` simply never gets
  blobs — the type is the discriminator the chunker reads.

`PDF` is `application/pdf`. `TEXT` is anything starting with `text/` —
plain-text files we can read without parsing. Everything else is `OTHER`.
Folders are filtered out at the Drive query level; they are not files.

## Sync is inline and transactional

`POST /data/files/sync` reconciles the user's `data_files` rows against
the live Drive listing. The contract:

- Files in Drive that we don't have → insert (state `PENDING`).
- Files we have that aren't in Drive → delete (cascading their blobs).
- Files in both → leave untouched (preserves `state` and existing blobs).

The endpoint runs the full reconciliation inline and returns counts when
done. We chose this over a fire-and-forget background job because:

- Listing Drive is the only network-bound work, and it scales with file
  count, not file size. Even large drives finish in seconds.
- A synchronous endpoint has trivial error semantics: the HTTP status
  reflects the outcome. A background job would need a job table, status
  endpoint, and retry policy — all of which are work we don't yet need.
- The diff itself is one transaction with two statements. Doing it inline
  means the database is never in a half-reconciled state visible to
  readers.

State preservation is why the upsert uses `ON CONFLICT DO NOTHING` rather
than overwriting. Sync should never undo processing work; that's the
chunker's job.

## Sync is scoped by a folder prefix

Drives are noisy. Most users keep the files they want Librarian to process
under a dedicated folder, and ingesting their entire drive would dilute
that signal with everything else. The sync endpoint therefore takes a
`prefix` (e.g. `/librarian/`) and only considers files reachable from that
folder.

A few constraints shape the implementation:

- **Drive has no path-prefix query.** Files have a `parents` reference and
  a `name`; "path" is a derived concept. Filtering by prefix means
  resolving the prefix to a folder ID by walking from root, then
  recursively listing descendants via `'<folderId>' in parents`. There is
  no Drive operator for "all descendants of folder X".
- **Empty prefix means the whole drive.** The empty/`/` case bypasses the
  folder walk and uses a single flat listing query — same result, far
  fewer API calls.
- **Missing prefix folder is a 404, not an empty result.** If a typo'd
  prefix were treated as "no files match", the sync's reconciliation step
  would silently delete every existing row for the user. We refuse to do
  that: a missing folder, or an empty match set, returns 404 and the
  reconciliation never runs.

The prefix is per-sync rather than persisted server-side. The frontend
keeps the user's last value in `localStorage` and sends it on each call.
This keeps the schema unchanged and gives the user a clear mental model:
"sync deletes rows that aren't in the current Drive scope". The cost is
that switching prefix wipes anything outside the new scope on the next
sync — a deliberate consequence of the user changing what they consider
in-scope.

## State counts over SSE

The frontend needs to surface progress to the user: "how many files do
I have, and how many are ready". This is naturally a stream — the
underlying counts change while sync (and, later, chunking) runs.

`GET /data/files/state-counts/stream` returns `text/event-stream` and
pushes a JSON `{pending, ready, total}` payload on a server-controlled
cadence (settings: `data_files.state_counts_interval_seconds`). The
choice of SSE over polling:

- The cadence is a server-side concern — it depends on what work is
  happening, what the database can serve, and what we want to charge the
  pool for. Server-pushed events let us tune that in one place.
- A single open request is cheaper than many short ones, both in HTTP
  overhead and in connection-pool churn.
- The browser primitive (`EventSource`) is small, standard, and handles
  reconnection automatically.

A subtlety: SSE responses are long-lived. If the endpoint held a pool
connection for its whole lifetime, a few connected browsers could starve
the database pool. The implementation acquires a connection per tick and
releases it immediately, so the long-lived part of the request never owns
a database resource.

## What's intentionally out of scope (for now)

- **Blob population.** `data_blobs` exists in the schema but no endpoint
  writes to it yet. The chunking pipeline is the next piece.
- **Mime-type updates.** If a file's mime type changes in Drive, the sync
  preserves the existing row (and its `type`). Reclassification is a
  separate concern — likely a small admin operation later.
- **Multi-source sync.** The schema and the sync function are
  parameterised on `source`, but only `GDRIVE` is wired up. Adding a new
  source is a new sync endpoint that calls the same `Table` methods.
- **Incremental sync.** Each call lists the full Drive. Drive's
  `changes.list` API supports cursored deltas; we'll add it once full
  listings stop being fast enough.
