# 08. Destructive sync controls

This document covers the two operator-facing endpoints added alongside
`/data/files/sync`, which let a user explicitly invalidate parts of the
pipeline and let the existing workers rebuild from a clean state. They
do not introduce any new data flow: they're a single DELETE statement
each, riding on the cascade triggers established in
`04.immutable_data_pipeline.md`.

## Goal

The pipeline is incremental by design: blobs that already exist stay,
the tree grows in place, and workers only do work when their `NOT
EXISTS` predicates select rows. That property is great until something
upstream changes: a different embedding model, a tweaked Abstract
schema, a buggy LLM run, or just an unhappy tree shape. In those cases
we want to be able to throw work away at a chosen layer and let the
workers reconstitute the rest from the layer below.

Two granularities cover the useful cases:

- **Rebuild tree** — keep files and blobs (the expensive LLM-generated
  artefacts), but discard the tree structure and node abstracts.
  `tree_builder` re-attaches every blob; `node_extractor` re-abstracts
  every node.
- **Clear library** — discard files, blobs, the tree, and abstracts —
  everything except the user account itself. The library is empty
  after this; the next `/sync` call repopulates files and the whole
  pipeline runs from scratch.

There is no "rebuild just the node abstracts" middle tier. That layer
already invalidates itself row-by-row when an upstream change touches
the structure (see "Group 4 — invalidation cascades" in
`04.immutable_data_pipeline.md`); a coarse "delete `data_node_abstracts`
for the user" would work but we haven't yet found a reason to expose
it. Easy to add later if we do.

## Implementation: one statement each, the schema does the rest

```
POST /data/files/rebuild-tree   →  DELETE FROM data_blob_edges WHERE user_id = $1
POST /data/files/clear         →  DELETE FROM data_files      WHERE user_id = $1
```

That's the entire backend. Both are 204-no-body. Auth is the standard
`CurrentUser` dep.

The cascades that make this work:

- Deleting `data_blob_edges` fires `data_blob_edges_invalidate_parent`
  (deletes the leaf's weight + abstract eagerly) and the deferred
  `data_nodes_drop_if_orphan` trigger. At commit time the orphan walk
  collapses the entire tree from the leaves upward — the root included,
  per migration `…0007`. Blobs and files are untouched; `data_blobs`
  rows simply no longer have any `data_blob_edges` row referencing
  them, which the `tree_builder` claim query already treats as "needs
  attaching." Workers pick the work back up on their next poll.
- Deleting `data_files` fan-outs through the FK chain:
  `data_blobs ON DELETE CASCADE` removes blobs, the `child_blob_id`
  UNIQUE FK on `data_blob_edges` removes blob_edges, the orphan
  trigger collapses the tree as above. `data_node_weights` and
  `data_node_abstracts` go with their nodes (`ON DELETE CASCADE` on
  `node_id`). The user_id stays. The next `/sync` recreates
  `data_files` rows; `blob_extractor` then re-extracts every blob;
  `tree_builder` and `node_extractor` follow.

Both DELETEs run inside a single explicit transaction so the deferred
orphan-collection trigger fires once at commit, with a fully-consistent
view. No worker coordination is needed: the existing per-(user_id)
advisory lock in `tree_builder` serialises any in-flight worker
iteration against the DELETE — the worker either commits before, or
re-reads the (now-empty) state after.

## API shape: split, not flagged

These could have been query-flag options on `/sync` (`?mode=rebuild`).
We chose three siblings because:

- Each endpoint does one obvious thing; URLs are self-documenting.
- Splitting matches the convention in `01.base_api.md` ("the folder
  hierarchy mirrors the URL hierarchy"); a single endpoint with mode
  flags would conflate three semantic actions.
- It eliminates a class of mistakes — `/sync` cannot accidentally
  destroy data; `/rebuild-tree` cannot accidentally fetch from Drive.

The trade-off (more endpoints to register) is negligible — both new
endpoints are five lines.

`/clear` is named to match what it actually does — clear the
library — rather than promising a re-sync that the endpoint doesn't
itself perform. Pairing a clear with a follow-up `/sync` is the
"start over from Drive" flow, and is left to the caller (FE today,
scripts/CI tomorrow). An earlier draft called this `/resync`, but
the name overstated the behavior: a network blip after the DELETE
would leave the user with an empty library and no clear next step,
whereas "Clear library" makes the next step obvious ("press Sync
when you're ready").

## FE: separate buttons, twice-confirmed

The Sync tab carries three buttons:

- **Sync from Drive** — primary action, no confirmation. Idempotent
  in practice (re-running picks up new files, deletes vanished ones).
- **Rebuild tree** — secondary, `variant="default"`. One
  `window.confirm` step: discards the tree and abstracts, keeps blobs.
- **Clear library** — secondary, `color="red"`. One
  `window.confirm` step with a sharper warning: discards everything,
  caller follows up with Sync from Drive when ready.

`window.confirm` is intentionally low-fi — Mantine `Modal` would also
work and matches the rest of the UI better, but the simplicity bar in
the FE is "deliberately simple" (CLAUDE.md) and a single confirm
dialog has the same outcome with one fewer state machine. Easy to
swap for a `Modal`-based confirmation later.

## What the worker side does (or doesn't do) about this

Nothing special. The workers' polling loops are already shaped around
"if there's work to do, do one unit, else sleep." A tree wipe makes
their `NOT EXISTS` predicates select many rows the next iteration; a
file wipe leaves nothing to claim until the next `/sync`. The user
gets to watch the pipeline counts (`/data/files/pipeline-counts/stream`)
move backwards as soon as the DELETE commits, then climb forward as
the workers refill the rows.

## What's intentionally out of scope (for now)

- **Partial wipes.** "Delete one file and its derivatives" already
  works via `DELETE FROM data_files WHERE file_id = ...` — there's no
  endpoint for it today, but the schema-level mechanism is identical
  to `/clear`'s. We expose the per-user form because that's the case
  users actually ask for; per-file management can be added when
  needed.
- **Re-extract on prompt or model change.** Updating the LLM model,
  embedding model, or the Abstract field set doesn't invalidate
  existing rows. Today the recipe is "/clear, then change the
  setting, then /sync." A more targeted path would be a worker-side
  generation marker, but that's a different change.
- **Undo.** Both endpoints are destructive. We rely on the
  twice-confirmed FE flow and the deterministic re-derivation from
  Drive to keep the cost of a mistake bounded (LLM cost + wall time,
  not lost source data).
