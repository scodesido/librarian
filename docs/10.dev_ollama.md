# 10. Dev Ollama image

The local compose stack runs a custom `librarian-ollama` image built from
[`ollama/dockerfile`](../ollama/dockerfile). Dev embedding models are
pulled during `docker build`, not on each container start.

## Why bake models at build time

Runtime startup uses the upstream image entrypoint (`ollama serve` as PID 1).
No init script, signal traps, or bootstrap/teardown dance is needed at run
time — only during the image build, where the temporary `ollama serve`
process does not survive the build step.

## No persistent volume

`/root/.ollama` is not bind-mounted. Models live in the image layer and are
visible at runtime. Anything pulled manually inside a running container is
lost when the container is recreated; change the model list in the
dockerfile and rebuild instead.

If you still have `.container_data/ollama` from an older setup, it is unused
and can be deleted.

## Adding or changing models

1. Add an `ollama pull <name>` line in [`ollama/dockerfile`](../ollama/dockerfile).
2. Rebuild: `docker compose build librarian-ollama`
3. To force a fresh registry pull: `docker compose build --no-cache librarian-ollama`

Build requires network access to the Ollama registry.

The default dev embedding model (`qwen3-embedding:0.6b`) matches
`embedding_model` in dev service settings. The default LLM
(`ollama:qwen3.5:9b`) is not baked; it is pulled on first use unless you add
it to the dockerfile.

## Compose service

`librarian-ollama` in [`docker-compose.yaml`](../docker-compose.yaml) builds
this image. `librarian-service` waits for it to become healthy before
starting. The healthcheck uses `ollama list` with a short start period
because models are already present.
