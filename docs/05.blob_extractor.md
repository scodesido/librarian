# 05. blob_extractor: from synced file to blob set

This document describes the first of the three workers introduced in
`04.immutable_data_pipeline.md`. The `blob_extractor`'s job is to take
a synced file, read its content from Drive, chunk it, generate per-blob
Abstracts and embeddings, and persist the whole blob set atomically.

## Goal

Sync produces `data_files` rows with `path`, `type`, and
`source_modified_at` set, nothing else. The `blob_extractor` is what
turns those rows into queryable material:

```
data_files (no blobs yet)
   ↓ blob_extractor
data_files (no row change — immutable)
   + data_blobs (linked list with abstracts + embeddings,
                 last one is_final_blob = TRUE)
```

A file is "ready" the moment its blob set is fully inserted. The
`is_final_blob` marker on the tail blob is the signal the rest of the
pipeline polls for.

## Atomic per file: one long transaction

The whole pipeline for one file runs **inside a single transaction**
on a single pool connection:

```
async with pool.acquire() as conn:
    async with conn.transaction():
        file = claim_next_unready_file(conn)   # FOR UPDATE SKIP LOCKED
        if file is None: return False
        pg_advisory_xact_lock(file.user_id, file.file_id)
        process_file(file, conn, ...)          # LLM + Drive + embed + INSERT
```

This is the deliberate consequence of immutability + state-by-existence:
without a `state` column to mark "we're working on this", the lock on
the file row IS the claim, and the lock must be held until the work is
durable.

The trade-off is a long-running transaction (typically tens of seconds,
sometimes minutes) that pins one pool connection while LLM and Drive
calls happen. We accept the pinned connection because:

- The alternative — a brief claim transaction with a state column — is
  exactly what the rest of the design is moving away from.
- Pool sizing is straightforward: a pool of `concurrent_workers +
  small slack` accommodates the worst case. The default 10-conn pool
  comfortably runs the default 1 concurrent worker.
- A long transaction prevents `VACUUM` on the touched tables for its
  duration, but those tables only grow by append from this worker, so
  there's nothing to vacuum mid-job anyway.

If the worker crashes mid-job, the transaction aborts: no blobs land,
no file row changes, and the row lock and advisory lock both release.
The next iteration of any worker can claim the same file and start
over from scratch.

## Why two locks (FOR UPDATE + advisory)

The `FOR UPDATE SKIP LOCKED` on `data_files` is the actual concurrency
primitive: any other worker scanning for unready files skips a
locked-by-someone row and tries the next one.

The `pg_advisory_xact_lock(user_id, file_id)` immediately after is
redundant in practice (the FOR UPDATE already excluded other workers)
but encodes intent. A future engineer reading the code, or splitting
the transaction into smaller pieces, will see the lock acquisition and
think twice about whether the split breaks the "one atomic unit per
(user, file)" contract. The cost is one trivial SQL call; the
documentation value is high enough to justify it.

## Vendor neutrality: pydantic-ai for the LLM, hand-rolled for the embedder

The two model calls each take a `"<provider>:<model>"` settings string,
but the layers underneath are different:

- **LLM (`build_llm_model`):** goes through `pydantic-ai`'s `Agent`
  with `output_type=RollingAbstract`. That gives us structured-output
  parsing for free across any provider pydantic-ai supports. The
  default is `"anthropic:claude-haiku-4-5"`; switching to a different
  Claude model, or to OpenAI / Gemini / Bedrock, is a settings change.
- **Embeddings (`build_embedder`):** dispatches on the provider prefix
  to a small per-provider class in `service/embedder.py`
  (`OllamaEmbedder`, `VoyageEmbedder`, …). Each is ~15 lines of direct
  HTTP against the provider's `/embeddings` endpoint, returning
  `list[NDArray[float32]]` for the shared `Embedder` Protocol. The
  default is `"ollama:qwen3-embedding"`, with `embedding_dimensions`
  passed through so Matryoshka-capable models truncate server-side to
  match the 1024-dim `data_blobs.embedding_blob` column.

The split is deliberate. pydantic-ai's value on the LLM side is the
structured-output plumbing; on the embedder side it's a thin wrapper
that buys us little while constraining us to whatever providers
pydantic-ai happens to support. Rolling our own embedder layer
unlocks first-class support for providers like ollama (which
pydantic-ai doesn't natively expose) and keeps the dependency
footprint small.

API tokens are passed explicitly into both layers from settings
(`blob_extractor.llm_api_token` for the LLM slot,
`blob_extractor.embedder_api_token` for the embedder slot), rather
than being read from env by the SDKs. Same rationale as before: the
secrets layer (which will eventually mount values as files) targets
the settings field. The tokens are per-slot, not per-provider: a
single `llm_api_token` field carries the credential for whichever
provider the `llm_model` string selects (anthropic, openai, xai,
…), and similarly for the embedder. This is the shape the future
"users provide their own key via the UI" flow expects — one field
per slot regardless of provider.

The `ollama_host` setting points at an ollama daemon. In docker-
compose the daemon runs as its own service (`librarian-ollama`) and
`ollama_host` resolves it via compose-internal DNS to
`http://librarian-ollama:11434`. The container uses the official
`ollama/ollama` image; an init script (`dev-config/ollama/init.sh`,
bind-mounted) starts `ollama serve` in the background, polls the
daemon until it answers, runs the dev `ollama pull` lines inlined in
the script, then `wait`s on the daemon. A SIGTERM/SIGINT trap re-
signals the daemon and waits for it to exit cleanly — without it,
POSIX sh wouldn't forward signals from PID 1 to the backgrounded
daemon, and `docker compose down` would end up SIGKILLing it via
Docker's 10s grace timer. The model cache lives on a bind-mounted
volume (`.container_data/ollama`, gitignored), so the pulls are
no-ops after the first start — they just check the registry for
updates. The service exposes a healthcheck (`ollama list`) that
gates `librarian-service` via `depends_on: service_healthy`, so the
worker doesn't start hitting embeddings before the daemon and the
model are ready. The daemon runs on CPU by default — fine for an
embeddings-only workload in dev; switching to GPU passthrough would
require additional compose plumbing we deliberately skip.

The earlier topology — host ollama reached via `host.docker.internal`
and an `extra_hosts: host-gateway` entry on `librarian-service` —
was retired when the container moved in-compose; the same env-var
override (`LIBRARIAN__BLOB_EXTRACTOR__OLLAMA_HOST`) is still
available for anyone who'd rather point at a host daemon.

## PDF blobs: three modes for the LLM, always text for the embedder

Files of type PDF are sliced into N-page sub-PDFs (default N=5) by
`pypdf.PdfReader` + `PdfWriter`. The half-open page range
`[file_start, file_end)` is 0-indexed; a 5-page first chunk has
`(file_start=0, file_end=5)`.

How the LLM sees each chunk depends on `blob_extractor.llm_pdf_mode`:

- **`text`**: the chunk is sent as pypdf-extracted plain text. Cheapest;
  works on any model; loses charts, layout, and anything scanned.
- **`binary`**: the chunk is sent as `BinaryContent(media_type=
  "application/pdf")`. Anthropic handles this natively (charts and
  layout survive); local models served via ollama's OpenAI-compat path
  reject the binary payload with "invalid message format".
- **`images`** (default, paired with the default `ollama:gemma3:4b`):
  each page of the chunk is rasterized to a PNG via PyMuPDF and sent
  as separate `BinaryContent(media_type="image/png")` parts. The
  vision-capable LLM gets to see exactly what's on the page; ~256
  tokens/page, well within gemma3's 128k context. DPI is configurable
  via `pdf_image_dpi` (default 150).

Regardless of mode, the **embedder** always sees pypdf-extracted text.
The text path is the lowest common denominator and matches the
embedder's text-only input shape. The concatenation also includes the
Abstract the LLM produced, so a chart-heavy or scanned blob still
yields a meaningful embedding via the Abstract — the LLM saw the
pages (in `binary` or `images` mode), and the embedder consumes its
synthesis.

## TEXT blobs: word-bounded character ranges

For TEXT files the chunker tokenizes on whitespace
(`re.finditer(r'\S+', text)`), groups every N words (default 1500),
and emits one blob per group. `file_start` and `file_end` are 0-based
half-open character offsets, so `original_text[file_start:file_end]`
recovers the blob's exact text. We chunk by words because "10 pages of
a PDF" is naturally analogous to "1500 words of plain text", but we
record by chars because retrieval needs to slice the original file.

## OTHER files are ignored, not deleted

Files of type `OTHER` (everything that isn't PDF or text/*) are
synced into `data_files` but skipped by every pipeline worker. The
`blob_extractor`'s claim query explicitly filters
`type IN ('PDF', 'TEXT')`. In the readiness queries, OTHER files are
counted as ready by fiat (they have no processable content), so they
don't keep the user's "files ready" count stuck below the total.

This replaces the previous "mark OTHER files READY via a state
column" approach with the more direct "filter them at the predicate
level" approach. No row writes are needed; OTHER files just live in
`data_files` indefinitely.

## Abstract: librarian-style classification + one anchored running summary

The Abstract carries the fields a librarian would index a document by,
all chosen so they make sense both at the blob level (this 5-page slice)
and at the node level after rollup by `node_extractor`:

```python
class Abstract(BaseModel):
    title: str               # short display label
    summary: str              # ~100 words, configurable
    topics: list[str]         # ~5 short topical labels
    key_questions: list[str]  # questions this content answers
    key_claims: list[str]     # explicit assertions / findings
    persons: list[str]        # named persons EXPLICITLY mentioned
    organizations: list[str]  # named orgs EXPLICITLY mentioned
    works: list[str]          # named works/laws/standards/products
    other_entities: list[str] # named entities not in the above buckets
    locations: list[str]      # geographical locations EXPLICITLY mentioned
    time_period: list[str]    # eras/dates the content is about
    language: list[str]       # natural languages used
    intended_audience: str
    domains: list[str]        # prefer one for leaves
    content_tags: list[str]   # closed-vocabulary subject facet — see docs/12.tags.md
    format_tags: list[str]    # closed-vocabulary genre facet — see docs/12.tags.md

class RollingAbstract(Abstract):
    running_summary: str = "" # ~80 words, configurable
```

`content_tags` and `format_tags` are the librarian-style facet tags
described in `docs/12.tags.md`. They're drawn from closed vocabularies
in `service/tags.py`, validated by Pydantic at parse time, and rolled
up deterministically at internal nodes — see that doc for why the
vocabularies are closed and how to grow them.

## Two-agent design: main + tag classifier

For each chunk, the blob extractor invokes **two** LLM agents serially:

1. The **main agent** (`build_main_agent` in
   `service/blob_extractor/abstract.py`) synthesizes the
   prose-and-entity fields and produces a `RollingAbstractCore` (the
   superclass `Abstract` minus the two tag facets). Tags are
   deliberately absent from its output schema, so the model never has
   to reason about them. The chunk content (text/binary/images
   depending on `llm_pdf_mode`) and the previous blob's
   `running_summary` are this agent's input.
2. The **tag agent** (`build_tag_agent` in
   `service/blob_extractor/tagging.py`) then classifies the chunk
   into `content_tags` + `format_tags` from the closed vocabularies.
   It reads only the main agent's compact output — title, summary,
   topics, domains — ~200 input tokens per call. Its output type
   `BlobTags` carries schema-level `enum` (via `Literal`) and
   `minItems: 1` constraints, so the model literally cannot return
   `[]` or an out-of-vocab string.

`process_file` then assembles a `RollingAbstract` from the two
outputs and re-validates — see `docs/12.tags.md` for the model
hierarchy and the rationale.

The two calls run serially (tag agent depends on main's output)
rather than concurrently against the raw blob — the latency cost is
modest (the tag call is small and fast) and the token savings are
real (the tag agent sees ~200 input tokens instead of duplicating the
multi-page chunk content).

Field *meanings* live as `Field(description=...)` on `Abstract` in
`service/abstract.py`. Pydantic-ai forwards those descriptions to the
LLM as JSON-schema property descriptions, so what each field is for
travels with the structured-output contract and the agent's
instructions don't have to restate it.

Per-field *budgets* (word counts, item caps) live in
`AbstractSettings` (`service/abstract_settings.py`), embedded as
`abstract: AbstractSettings` on each worker's settings — so blob and
node can be tuned independently in YAML (e.g. node summaries can grow
longer near the root without touching the blob path). `AbstractSettings`
also owns the rendering of those budgets into instruction text via two
`@property` helpers: `budgets_text` (base `Abstract` fields) and
`rolling_budgets_text` (adds the `running_summary` line, for the
blob agent whose output type is `RollingAbstract`). Each agent
builder interpolates the appropriate helper into its instructions —
so the budget shape is defined once, in `AbstractSettings`, and
neither agent has to know how the lines are formatted.

The entity buckets and `locations` carry an "EXPLICITLY mentioned;
leave empty otherwise" rule — both in their Field descriptions and
restated once in the agent instructions. At the blob level the rule
binds to the blob's own text; at the node level (handled by
`node_extractor`) it binds to what's already in the children's
Abstracts, so the explicit-only constraint propagates up the tree
without re-inventing entities.

`running_summary` is the only field that reaches across blobs: for
the first blob of a file the agent infers the document's overall
theme from the first blob alone; for subsequent blobs the prompt
includes the previous blob's `running_summary` and asks the agent
to weave the new blob into it. The chain is the reason
`blob_extractor` processes one file end-to-end within a single
worker run.

The Abstract is stored as a JSONB column on `data_blobs.abstract`.
There is no separate "embed each field" table this time around —
just one embedding per blob, computed from raw text + selected
Abstract fields concatenated (see below).

## Two embeddings per blob

Each `data_blobs` row carries two `vector(1024)` columns:

- `embedding_blob` — encodes the blob's own content as
  `normalize(raw_vec + abstract_vec)`, where `raw_vec` is the
  embedding of the blob's raw text and `abstract_vec` is the
  embedding of `serialize_abstract_for_embed(abstract)`. Each stream
  is independently chunked (bounded by `embedding_chunk_chars_max`,
  so we stay under the embedder's context limit), mean-pooled across
  its sub-chunks, and L2-normalised. The blob vector is then the
  L2-normalised sum of the two stream vectors — equivalent to a
  midpoint direction. If the raw text is empty/whitespace (e.g. an
  image-only PDF chunk where pypdf extracted nothing), the blob
  vector is just `abstract_vec`. Embedding the abstract as its own
  stream gives it the same weight as the raw text regardless of raw
  length, which is the point: the abstract carries the librarian-
  style classification that node-level rollups reuse.
- `embedding_with_file` — `normalize(embedding_blob + file_embedding)`,
  where `file_embedding = normalize(sum(embedding_blob))` over all
  blobs of the file. Also L2-unit.

The point of `embedding_with_file` is to bias the descent algorithm
in `tree_builder` so that blobs of the same file tend to land under
the same leaf node. The pure `embedding_blob` remains available for
retrieval, where we don't want this bias.

Both are computed in memory in a single batched embedder call — one
network round-trip per file, regardless of blob count or stream
count, with the per-blob/per-stream reduction done locally on the
returned vectors before the INSERTs run.

`serialize_abstract_for_embed` concatenates the prose-bearing fields
of the Abstract: `title`, `summary`, `intended_audience`,
`", ".join(topics)`, `", ".join(domains)`, `", ".join(content_tags)`,
`", ".join(format_tags)`, `", ".join(time_period)`,
`"\n".join(key_questions)`, `"\n".join(key_claims)`, and
`running_summary`. Empty fields are skipped so they don't introduce
stray separators. The pure-label fields that are *not* embedded —
`content_type`, the entity buckets (`persons`, `organizations`,
`works`, `other_entities`), `locations`, `language` — stay filter-
side: they're short labels and named references, more useful as
JSONB filters than as similarity anchors.

`content_tags` / `format_tags` break that pattern deliberately: they're
short closed-vocabulary labels but we include them in the embedding
stream so shared tags pull tag-similar blobs together during
`tree_builder` descent, which tightens the set-unions at internal
nodes. See `docs/12.tags.md` for the full rationale.

## End-to-beginning insertion

The blob set is inserted in **reverse** order: the tail blob first
with `is_final_blob = TRUE, next_blob_id = NULL`, then each preceding
blob with `is_final_blob = FALSE, next_blob_id = <id of the blob
inserted just before>`. By the time the first blob lands the chain is
complete and well-formed.

This ordering is what lets the chain invariant
(`(next_blob_id IS NULL) = is_final_blob`) stay enforced row-by-row
rather than deferred to commit time. It also keeps the partial unique
index `data_blobs(file_id) WHERE is_final_blob` satisfied throughout:
there is exactly one tail row at every moment.

## Failure handling: per-worker exponential backoff

Any exception thrown by a worker iteration aborts its transaction
(losing all in-flight work for that file) and triggers a backoff sleep
on the worker. The next iteration tries again — picking the same file
(if it's still the oldest unready one) or a different one.

The backoff is per-worker, not per-file: a worker tracks its own
consecutive-failure streak and resets the streak to the floor on the
next successful iteration. A single bad file can therefore make the
worker that picks it up appear slow, but other workers (and other
files in the queue) are unaffected.

There is no `FAILED` state, no failure table, no "retry count" column.
A persistently-broken file keeps getting picked up, keeps throwing,
and keeps generating log entries that the operator can spot. If that
turns out to be too noisy in practice, the natural addition is a
small immutable `data_file_failures(file_id, attempted_at, reason)`
table that the readiness predicates exclude from — but we don't have
that today.

## Concurrency: many files, one at a time per worker

`concurrent_workers` (default 1) is how many copies of `worker_loop`
run in one process. Each loop runs one iteration at a time and owns
its own pool connection during a job. Increasing `concurrent_workers`
also requires the connection pool's `max_connections` to grow in
proportion — the long lease on the connection is the constraint that
matters.

There is no separate "stale claim sweeper" task (which the previous
state-machine design needed). Crash recovery is implicit: the worker
dies, its transaction rolls back, locks release, and the next
iteration of any worker re-picks the same file.

## What's intentionally out of scope (for now)

- **`source_modified_at`-driven re-processing.** The column is in
  `data_files`; the sync endpoint doesn't yet populate it or branch
  on it. When that lands, "file modified upstream" will trigger a
  delete-and-resync, which cascades to blob deletion via the FK, and
  the next `blob_extractor` iteration picks up the fresh file.
- **Streaming downloads / partial PDFs.** Drive files are fetched
  whole into memory. For very large PDFs this would matter; for the
  current workload it doesn't.
- **Custom prompts per `content_type`.** The Abstract agent's
  instructions are one fixed string. Specialising per detected type
  could improve quality but requires an extra LLM pass to classify
  first.
- **Re-embed on model change.** If we ever change `embedding_model`,
  existing rows keep their old vectors. A migration that wipes blobs
  (cascading the relevant tree edges and forcing a rebuild) is the
  natural way to roll a new encoder; we'll cross that bridge when we
  need to.
