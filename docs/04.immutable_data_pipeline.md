# 04. The immutable data pipeline

This document describes the data model that sits on top of `data_files`
and `data_blobs` (`03.data_files.md`): the abstraction tree, its
auxiliary 1:1 tables, and the rules that keep the whole thing coherent
without explicit coordination between the workers that maintain it. The
worker-specific concerns — `blob_extractor`, `tree_builder`,
`node_extractor` — are covered in the documents that follow.

## Goal

Each blob carries one chunk of one source file. To answer questions
across a user's library we build a tree of progressively higher-level
abstractions over those blobs. Each non-leaf node is a synthetic
summary clustered from a group of children one level below; retrieval
walks down that tree from the most general node to the most specific
relevant ones.

The model has to support:

- Many small per-blob facts (the leaves), produced by parsing source
  files with an LLM.
- Many internal nodes built by clustering nodes one level down, each
  carrying its own LLM-generated abstract.
- Incremental construction: new files arrive, the tree is updated
  without throwing away prior work.
- Multiple workers running in parallel, possibly across users, without
  explicit coordination beyond the database.
- Crashes at any point that leave the database in a consistent state
  the next worker iteration can resume from.

## The guiding rule: immutable rows, state by existence

Every table in the `data_*` family is **immutable**: rows are inserted
and deleted, never updated. The DB enforces this with a
`BEFORE UPDATE` trigger that raises an exception on any attempt to
modify a row. Once written, the row's content is the truth until the
row goes away.

This is the deliberate inverse of the earlier design (which had
`PENDING/PROCESSING/READY/FAILED` state columns on `data_files` and
`tree_nodes`, plus a `tree_state.level` gate). Immutability buys us:

- A row is either there or not. There are no half-transitioned states
  to reason about, no "is this PROCESSING flag stale?" recovery code.
- Workers coordinate through `EXISTS`/`NOT EXISTS` queries, not through
  state-machine transitions. Concurrency is simpler to verify locally:
  you only need to look at what creates the row and what deletes it.
- Crash recovery is built-in: a worker that died mid-job committed no
  rows, so the next iteration's `NOT EXISTS` predicate still selects
  the same work.

Where the previous design tracked "is this file ready?" by reading
`data_files.state = 'READY'`, the new design tracks it by reading
`EXISTS(SELECT 1 FROM data_blob_file_embeddings WHERE file_id = $1)` — a
row there only ever exists as part of a complete set (see
`19.per_blob_processing.md`), so its presence alone proves the file is
fully processed. Where the previous design wiped `tree_nodes WHERE height > 0` on every
new file, the new design lets the tree grow incrementally and uses
trigger-driven cascade DELETEs to invalidate only what's strictly
stale.

## The tables

| Table | Role | 1:1 with |
|---|---|---|
| `data_files` | files we know about | — |
| `data_file_manifests` | how many blobs a file should have + parse metadata | `data_files` |
| `data_blobs` | per-file chunks (abstract + own-content embedding) | — |
| `data_blob_file_embeddings` | file-relative embedding per blob | `data_blobs` |
| `data_nodes` | internal/leaf tree nodes | — |
| `data_node_edges` | parent→child edges between two nodes | — |
| `data_blob_edges` | parent→child edges from a leaf node to a blob | — |
| `data_node_weights` | centroid + blob_count per node | `data_nodes` |
| `data_node_abstracts` | LLM-generated Abstract per node | `data_nodes` |

The split of "node has a weight" and "node has an abstract" into two
separate 1:1 tables is load-bearing: they're computed by different
workers (`tree_builder` and `node_extractor`) at different times, and
each carries its own readiness predicate. Merging them would force one
INSERT to wait for the other; the split lets each flow independently.

The blob side mirrors this. `data_blobs` carries the intrinsic per-blob
content (the LLM Abstract + the own-content `embedding_blob`) and is
built **one blob at a time**; `data_blob_file_embeddings` carries the
file-relative `embedding_with_file` that `tree_builder` uses, derived
from the whole file's blobs and inserted as one atomic batch once the
set is complete. `data_file_manifests` sits above both and records how
many blobs the file must yield (its `expected_blob_count`), which is the
denominator the completeness checks key on. See
`19.per_blob_processing.md` for the full design and the trigger-enforced
integrity model.

## Readiness is a query, not a column

The "is this layer of the pipeline done?" question is answered by a
predicate over which rows exist. The canonical predicates live in
`librarian/db/readiness.py`:

- **File ready** — a `data_blob_file_embeddings` row exists for the file.
  Because those rows are inserted only as a complete set (all
  `expected_blob_count` of them, each backed by a blob), one existing row
  is sufficient proof. Files of type `OTHER` are treated as "always
  ready" by fiat (they have no processable content).
- **File's blob set complete (but maybe not yet file-embedded)** — a
  `data_blobs` row exists at `file_blob_index = expected_blob_count - 1`.
  The contiguity trigger forbids holes beneath it, so the top index
  existing implies the whole `0..k` prefix exists.
- **All blobs inserted into the tree** — every `data_blobs` row has a
  matching `data_blob_edges` row.
- **Tree ready for extraction** — all blobs inserted into the tree AND
  every `data_nodes` row has a matching `data_node_weights` row.
- **Tree ready for retrieval** — extraction-ready AND every
  `data_nodes` row has a matching `data_node_abstracts` row.

The cost is that each predicate runs a `NOT EXISTS` or `LEFT JOIN`
anti-join. With the supporting indexes (the `idx_data_blob_file_embeddings_file`
index for "file ready", and `UNIQUE(file_id, file_blob_index)` for the
"blob set complete" probe) the hot path is index-only. We accept the
heavier query cost in exchange for the simplicity of
state-by-existence; a caching layer can come later if it becomes a
bottleneck.

## Trigger cascades carry the invariants

The DB triggers are where most of the design lives. They fall into
four groups:

### Group 1 — immutability

Every table has `BEFORE UPDATE EXECUTE FUNCTION prevent_any_update()`,
which raises. There is no escape hatch; if a row needs to change, it's
deleted and re-inserted.

### Group 2 — structural integrity

These triggers fire at write time and reject malformed edges:

- `data_node_edges.parent.height = child.height + 1`.
- `data_blob_edges.parent.height = 0`.
- `data_*_edges.user_id` must match both endpoints' `user_id`.
- `data_node_weights.user_id`, `data_node_abstracts.user_id` must match
  the joined `data_nodes.user_id`.

The `user_id` consistency check is belt-and-suspenders against
cross-user joins: every read query already filters by `user_id`, but a
trigger means an accidentally-omitted filter at the write side fails
loudly rather than silently mixing data. If the trigger ever becomes a
performance bottleneck it can be dropped without touching data.

### Group 3 — deferred structural cleanup

Two constraint triggers run as `DEFERRABLE INITIALLY DEFERRED`, firing
at commit time so that within a single transaction we can dismantle
and reassemble structure freely:

- `data_nodes_check_root_unique` — at most one `is_root = TRUE` node
  per user. Deferred so a tree rebuild can swap roots in a single tx.
- `data_nodes_drop_if_orphan` (attached to `data_node_edges` and
  `data_blob_edges` `AFTER DELETE`) — a node with no outgoing edges
  at commit time is deleted, root or not. The deletion cascades to
  its incoming edges, which fire the trigger one level up, collapsing
  orphan subtrees naturally and tearing the root down with them when
  the last child disappears. The next insertion in tree_builder
  recreates the root lazily at height 0.

### Group 4 — invalidation cascades

These triggers carry the "if X changes, Y is now stale" relationships
across tables. They fire eagerly (not deferred); a stale row is removed
the moment it becomes stale, and the workers re-create it on their
next pass.

```
edge inserted/deleted          weight inserted/deleted        abstract inserted/deleted
   on data_node_edges               on data_node_weights           on data_node_abstracts
   on data_blob_edges
        |                              |                              |
        v                              v                              v
   DELETE parent's              DELETE parent's              DELETE parent's
   data_node_weights            data_node_weights            data_node_abstracts
   data_node_abstracts          (recurses up)                (recurses up)
   (eager, per-row)
```

The two transitive cascades (`data_node_weights` invalidating parents'
weights, `data_node_abstracts` invalidating parents' abstracts) are
symmetric because both quantities are derived from their children's
quantities; if a deep grandchild changes, the path of stale ancestors
extends to the root.

The edge-side cascade and the weight/abstract-side cascade compose: a
child's structural change triggers the edge-cascade, which deletes the
child's weight/abstract; that deletion triggers the
weight/abstract-cascade, which propagates upward through ancestors via
existing edges. A worker that picks the work back up will see exactly
the set of rows it needs to recompute, no more, no less.

### Group 5 — blob-set completeness, anchored on the manifest

The blob layer is built incrementally (one `data_blobs` row at a time;
see `19.per_blob_processing.md`), so a *partial* blob set is a normal
in-progress state, not a corruption. The integrity goal is narrower and
stronger: no write the application could perform may leave a file
*looking* complete when it isn't. Three triggers carry that:

- `data_blobs_check_against_manifest` (`BEFORE INSERT`) — a blob's
  manifest must exist, its `user_id` must match, and its
  `file_blob_index` must fall in `[0, expected_blob_count)`. A blob can
  never outrun or precede its manifest.
- `data_blobs_check_contiguous` (`DEFERRABLE INITIALLY DEFERRED`
  constraint trigger) — at commit, a file's blob indices form a
  contiguous `0..k` prefix (or are empty). This is what makes the "blob
  at index `expected_blob_count - 1` exists" completeness probe
  trustworthy: no hole can sit beneath the top index. It must be
  deferred because a cascade delete removes sibling rows in arbitrary
  order, which would trip a row-level guard mid-statement.
- `data_blob_file_embeddings_check_all_or_none` (deferred constraint
  trigger) — a file's file-embedding rows number either 0 or exactly
  `expected_blob_count`, so a single existing row proves the whole
  pipeline for that file is done.

The old "delete any blob → delete the owning file" backstop is gone: it
defended the linked-list / single-tail invariants of the all-at-once
design, which no longer exist (`next_blob_id` and `is_final_blob` were
removed). Invalidation is now `DELETE FROM data_file_manifests WHERE
file_id = $1`, which cascades to the blobs and their embeddings while
leaving the `data_files` row in place for re-extraction. Every other
deviation lands in the safe direction — the file reads as *not* ready
and the worker re-derives.

## Three workers, no shared state besides the DB

| Worker | Atom | Coordination |
|---|---|---|
| `blob_extractor` | one file, processed blob-by-blob | session-level `pg_advisory_lock(user_id, file_id)` held across many short transactions (one per blob, plus the manifest and the file-embedding batch); auto-released on crash |
| `tree_builder` | one weight backfill OR one file's blob insertions OR one node split | `pg_advisory_xact_lock(user_id)` per logical iteration |
| `node_extractor` | one node's abstract | `FOR UPDATE SKIP LOCKED` on a candidate `data_nodes` |

Each worker is structured as a polling loop with **per-worker
exponential backoff** on exceptions (`service/backoff.py`): the
worker sleeps with bounded exponential growth on consecutive
failures (default 5s → 5min, multiplier 2), and resets to the floor
on the next successful iteration. There is no separate failure
table; a persistently-poisoned file simply keeps falling into the
worker's backoff cadence, which surfaces in logs without halting the
rest of the pipeline. Monitoring/alerting on repeated failures is
deferred until we feel the pain.

The atoms are picked to bound the cost of a crash to one blob's LLM +
embed work (`blob_extractor` commits per blob; see
`19.per_blob_processing.md`), one centroid recomputation
(`tree_builder`), or one node (`node_extractor`). No worker holds state
across iterations except its own backoff timer.

## What's intentionally out of scope (for now)

- **Retrieval.** Walking the tree to answer a query is a separate
  concern. The schema is shaped to make it efficient (centroids,
  blob_counts for traversal priors) but no retrieval endpoint exists
  yet.
- **Cross-user trees.** Each user has their own tree. There is no
  global index; retrieval is per-user.
- **A persistent failure table.** A bad file retries forever on its
  worker's backoff schedule. We accept that for now in exchange for
  schema simplicity; if a "give up after N attempts" semantic becomes
  necessary, the natural addition is a small immutable
  `data_file_failures` table that the readiness query excludes from.
- **Multi-model embeddings.** One embedding model is hardcoded
  (`vector(1024)`). The earlier `(field, model_id)` shape for
  `node_embeddings` is gone; if we need to roll out a new model
  alongside the current one, the natural move is a parallel column or
  table.
