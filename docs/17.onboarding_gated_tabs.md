# 17. Onboarding-gated tabs and the Account panel

This document describes the FE reshaping of the home screen into a
sequential onboarding flow, and the redesign of the former Settings tab
into an **Account** panel. It supersedes the "Frontend: the Settings tab"
section of [14. User settings](14.user_settings.md) — the storage model,
endpoints, and credential resolution there are unchanged; only the FE
surface they back is rebuilt.

## Goal

The home screen had four peer tabs — Sync, Tree, Search, Settings — all
reachable in any order. A first-time user could land on Search before
saving a single API token, get a 409, and have to reverse-engineer that
they needed to visit Settings first. The pieces were all there; the
ordering told no story.

The fix is to make the tabs a **path**, not a menu. There is a natural
dependency chain:

1. **Account** — pick models, paste tokens. Nothing works without this.
2. **Sync** — pull files from Drive and let the pipeline build the tree.
   Pointless until the workers have credentials to run.
3. **Search** — query the tree. Pointless until the tree is built.

So the tabs render in that order and each later step is **disabled until
its prerequisite is met**. The chain is also why Tree leaves the user UI
entirely (see "Tree moves to admin" below) — it was a debugging view, not
a step in the user's journey.

## Tab order and gating

`home/home-screen.tsx` renders three tabs: **Account · Sync · Search**.

Two readiness signals gate them:

- **`accountReady`** — every slot whose selected model requires a token
  has one saved. This is the same condition the workers enforce as
  `MissingTokenError` and the Account panel shows as a per-row badge: a
  non-Ollama model with no token is "not ready". An all-Ollama setup is
  ready with zero tokens.
- **`syncReady`** — the existing `fullyReady` criterion: every pipeline
  stage (files, blobs, nodes) has at least one item and has fully
  processed all of them.

Gating:

| Tab     | Enabled when                       |
|---------|------------------------------------|
| Account | always                             |
| Sync    | `accountReady`                     |
| Search  | `accountReady && syncReady`        |

When the user clears the library or swaps a model to one that newly needs
a missing token, the relevant tabs re-disable live.

## Where the readiness state lives

Both signals are needed by `HomeScreen` (to gate tabs) but were previously
owned inside the panels. Rather than gate from inside the panels (which
can't reach sibling tabs) or duplicate the work, `HomeScreen` owns two
hooks and threads what the panels need back down:

- **`home/use-pipeline-counts.ts`** — owns the single
  `/data/files/pipeline-counts/stream` `EventSource`, exposes
  `{ counts, streamError }`, and carries the `syncFullyReady(counts)`
  predicate. `SyncPanel` now takes `counts`/`streamError` as props instead
  of opening its own stream — one SSE connection backs both the progress
  bars and the Search gate.
- **`home/use-account-readiness.ts`** — fetches `/settings/me` +
  `/settings/tokens` and computes `accountReady`. It deliberately does
  *not* share state with the Account panel (which fetches the same plus
  catalog + usage and owns the mutations). Instead the panel takes an
  `onChanged` callback and calls it after every save/delete; the hook
  exposes `refresh()`, which bumps a `tick` that re-runs its fetching
  effect. The cost is two cheap GETs duplicated on load; the benefit is
  the panel stays the single owner of its mutation/refetch logic.

The alternative — lifting *all* of the Account panel's data into
`HomeScreen` and passing it down — was rejected: it would thread the
panel's catalog/me/tokens/usage state and every mutation handler through
props for the sole benefit of a boolean the `onChanged` callback already
keeps in sync.

## Remembered-but-clamped active tab

The tabs are controlled. The user's last-chosen tab is persisted to
`localStorage` (`librarian.active_tab`) and restored on load, but the
**rendered** tab is clamped to what's currently enabled: if the stored tab
is gated, the furthest-enabled tab shows instead. Because we store the
user's *intent* and only clamp at render, a tab re-enabling (e.g. sync
finishing while the user waits) snaps the view back to where they wanted
to be — Search — rather than stranding them on Sync.

## The Account panel

`account/account-panel.tsx` (moved from `settings/settings-panel.tsx`;
component `AccountPanel`). The backend API stays `/settings/*` — those
genuinely are settings, and the panel may grow more account-level
concerns over time, which is also why the tab reads "Account". Two
sections now, down from three:

### Models & tokens, merged into one table

The old panel had a Models card (six selects + one batched "Save models"
button) and a separate Tokens card. The Tokens card carried a two-mode
toggle — "use one value for all slots" (a shared input + apply-to-all)
versus six individual inputs — which users found confusing, and whose
shared mode overflowed on narrow viewports because each slot's long label
and its status badge were forced onto one `space-between` line.

Both are replaced by a single **Models & tokens** Mantine `Table`, one row
per slot, columns: *Slot · Model · API token · actions · Status*. A fixed
table layout keeps every control in its lane regardless of label length —
this is the structural fix for the overflow. Per row:

- **Model** — a `Select` from the catalog that **auto-saves on change**.
  Picking from an operator whitelist is a setting toggle, not a draft you
  compose and commit, so there's no "Save models" button anymore.
- **API token** — a write-only `PasswordInput`, deliberately narrow (it's
  for pasting, not typing). Disabled when the model needs no token and
  none is saved.
- **actions** — *Save* (commits the typed token), *Copy above*, *Remove*.
- **Status** — a badge: *No token needed* (Ollama), *Saved*, or
  *Token required* (non-Ollama, no token).

### Copy-above replaces the two-mode toggle

The shared/per-slot toggle is gone. The common case — one key across every
slot — is now: paste the token in the first row, then click **Copy above**
down the column. Copy-above pulls the *typed* value from the row directly
above (tokens are never read back from the server, so it can only copy
what's still in the input) and **saves it immediately** — one click per
row, no mode to discover. Because the cascade needs a source, a typed
value is deliberately *not* cleared after a save.

This trades a little repetition (one click per slot vs. one apply-to-all)
for the elimination of a confusing modal toggle, which was the stated
priority. A user who wants genuinely different keys per slot just pastes
different values instead of clicking copy-above — the same UI serves both
cases without a switch.

The **Usage** section (read-only per-(operation, model) totals) is
unchanged.

## Tree moves to admin

The Tree explorer leaves the user UI. It was always a debugging view —
walking the raw node hierarchy isn't part of a user's journey — and it
doesn't fit the three-step onboarding chain. It moves to a separate admin
panel with a user selector, behind a single operator password and ssh.
`home/tree-explorer.tsx` stays in the tree for now and relocates to a
shared component dir when the admin panel lands; see the admin-panel
document (forthcoming) for that design.

## What's intentionally out of scope (for now)

- **Auto-advancing the tab.** Gating disables later tabs but never
  *navigates* for the user — finishing token entry doesn't jump them to
  Sync. The remembered-tab logic only clamps; it doesn't push. A guided
  "next step" nudge is a later, additive concern.
- **Explaining *why* a tab is disabled.** Disabled tabs have no tooltip
  (Mantine tooltips on disabled buttons don't fire reliably). The Account
  panel's per-row badges already say what's missing; a disabled-tab
  explainer can come back if users ask.
- **Sharing the readiness fetch with the panel.** The account-readiness
  hook re-fetches me+tokens rather than reading the panel's state. Two
  cheap GETs on load; revisit only if it shows up in practice.
