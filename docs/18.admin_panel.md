# 18. Admin panel: dual-target frontend and the `/admin` surface

This document describes the admin panel — a debugging surface with a user
selector and the tree explorer (relocated out of the user UI in
[17. Onboarding-gated tabs](17.onboarding_gated_tabs.md)). It is built from
the *same* frontend project as the user webapp via a build target, and
backed by a small `/admin` API gated by a single operator password.

## Goal

The tree explorer was always a debugging view — walking the raw node
hierarchy isn't part of a user's journey, and it has no place in the
three-step onboarding flow. But it's genuinely useful for the operator to
inspect *any* user's tree. So it moves to an admin panel that:

- can select **which user** to inspect (the user app is session-scoped to
  one user; admin needs to cross that boundary);
- sits behind **ssh** in production — it's an operator tool, not a public
  surface — with a single shared password as a lightweight second gate,
  not a user/role system;
- **reuses** the existing tree components and tooling rather than spawning
  a second frontend project.

## One project, two build targets

The admin panel and the user webapp differ in exactly one thing: which
root component mounts. Tooling, dependencies, `index.html`, `nginx.conf`,
`public/settings.js`, the tsconfigs — all identical. So rather than a
second Vite project (which would duplicate and drift all of that), the two
are **one project selected by a build-time env var**.

`main.tsx` branches on `import.meta.env.VITE_APP_TARGET`:

```tsx
const Root = import.meta.env.VITE_APP_TARGET === "adminpanel" ? AdminApp : App;
```

Because Vite statically replaces `VITE_APP_TARGET` at build time, the
ternary constant-folds and Rollup tree-shakes the unused app (and its
imports) out of each bundle — the webapp build contains no admin code and
vice versa. This relies on `App`/`AdminApp` having no top-level side
effects (they don't); worth a sanity grep of the built bundle if that ever
changes. If a hard guarantee is ever needed, switch the branch to a
dynamic `import()` of the chosen root.

### Why an env-branch and not separate HTML entries / MPA

A Vite multi-page setup (`index.html` + `admin.html`) would work for
`vite build` but is awkward in `vite dev`: the dev server serves
`index.html` at `/`, so the admin app would live at `/admin.html` or need
`root`/rewrite fiddling. Since the two run as **separate containers on
separate ports** (`:3000` webapp, `:3001` admin), the env-branch keeps `/`
correct in each container with zero dev-server gymnastics — the dev server
inherits the baked target and mounts the right root.

### Dockerfile: one file, one ARG

`frontend/dockerfile` is parameterized:

```dockerfile
ARG APP_TARGET=webapp
ENV VITE_APP_TARGET=$APP_TARGET
```

The default builds the webapp; `--build-arg APP_TARGET=adminpanel` (or the
compose `build.args`) builds the admin panel. The `ENV` flows into both
`npm run build` (prod stage) and the dev server launched by the entrypoint,
so the single file covers both modes. `docker-compose.yaml` runs two
services off this one Dockerfile — `librarian-webapp` (default args) and
`librarian-adminpanel` (`args: APP_TARGET: adminpanel`), on `:3000` and
`:3001`. The prod stage's `dist` and nginx SPA fallback are unchanged;
since the two are separate images there's no output collision.

## Shared tree component

`TreeExplorer` moves to `frontend/src/components/tree-explorer.tsx` and is
parameterized by a `loadNode(nodeId) => Promise<Response>` callback instead
of calling the user `api` client directly. The user app would pass a loader
hitting `/data/tree`; the admin panel passes one hitting
`/admin/tree?user_id=…`. `loadNode` must be referentially stable (it's an
effect dependency); switching the inspected user **remounts** the explorer
via a React `key={userId}`, which resets navigation to the root rather than
stranding the view on a node id from the previous user's tree.

## The `/admin` API

Two routers under `endpoints/admin/`, both gated at the router level by a
`require_admin` dependency:

```
GET /admin/users                       → [{user_id, user_name, created_at}]
GET /admin/tree/node?user_id=…         → NodeView (root)
GET /admin/tree/node/{node_id}?user_id=… → NodeView
```

`/admin/tree` deliberately imports `NodeView` + `build_node_view` from the
user-facing `endpoints/data/tree` — the only difference between the two is
where `user_id` comes from (an explicit query param vs. the session
cookie), so there's no second copy of the view logic. The db layer
(`db/tree_children.py`) was already `user_id`-scoped, so nothing below the
endpoint needed to change. `/admin/users` adds a single `Users.list_all()`.

### Auth: one password, header-carried, fail-closed

`api/core/auth/admin.py` exposes `require_admin`, which compares the
`X-Admin-Password` header against `settings.admin.password` with
`secrets.compare_digest` (constant-time). Two distinct refusals:

- **503** when no password is configured — admin is opt-in per environment
  and fails *loud*, never silently open;
- **401** when the header is missing or wrong.

This is deliberately not a session/cookie flow: the panel is behind ssh and
short-lived, so the password is held in the browser tab's `sessionStorage`
and attached as a header on each request (`admin/admin-client.ts`).
Validation is optimistic — the first `/admin/users` call confirms the
password, and a 401 flips the UI back to the login screen. No admin
session table, no cookie, no token issuance: the smallest thing that gates
a debug tool.

### CORS

The admin panel is a distinct origin (`:3001`) and sends a non-simple
header (`X-Admin-Password`), so the operator's `api.cors_origins` must
include the admin origin and `api.cors_headers` must include
`X-Admin-Password` for the preflight to pass. The dev config
(`dev-config/api/settings.yaml`) sets both, plus a dev `admin.password`.

## What's intentionally out of scope (for now)

- **Admin users / roles.** One shared password, not accounts. The panel is
  behind ssh; richer auth is unmotivated until there's more than one
  operator or write operations.
- **Write/debug actions.** The panel is read-only (inspect a user's tree).
  Destructive or repair actions (re-trigger a user's pipeline, edit a node)
  would each want their own gated endpoint and a confirmation flow.
- **Admin-only API hardening.** `/admin` shares the same FastAPI app and
  CORS policy as the user API. Behind ssh that's fine; a public deployment
  would want the admin surface on a separate bind/origin.
- **Hard bundle isolation.** The webapp/admin split relies on build-time
  tree-shaking, not separate entry points. Good enough; revisit only if a
  bundle audit shows cross-contamination.
