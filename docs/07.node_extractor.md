# 07. node_extractor: per-node Abstracts, bottom-up

This document describes the third of the three workers introduced in
`04.immutable_data_pipeline.md`. The `node_extractor`'s job is to
produce one `data_node_abstracts.abstract` row per tree node, using
the LLM to synthesize from the children's Abstracts.

## Goal

Once `tree_builder` has settled a user's tree, every blob is anchored
under a leaf node and every internal node has a centroid. What's
missing is the *semantic* layer: each non-leaf node needs an Abstract
that summarizes its subtree, so retrieval can walk down using both
geometry (centroids) and semantics (abstracts).

`node_extractor` fills that gap bottom-up. A node is "extractable"
when every one of its children already has an Abstract, where:

- A **blob child** always has one (`data_blobs.abstract` is `NOT NULL`,
  written by `blob_extractor`).
- A **node child** has one iff its `data_node_abstracts` row exists.

So extraction proceeds from height 0 upward: leaf nodes first (whose
blob children are immediately ready), then height-1 internal nodes,
and so on to the root.

## Per-iteration atom: one node's Abstract

Each worker iteration performs **exactly one node's** abstract
computation, inside one long transaction:

```
loop:
  acquire conn; begin tx
    pick a user whose tree is ready for extraction AND has unprocessed nodes
    if none: end tx; sleep(poll_interval); continue
    claim a candidate node (FOR UPDATE SKIP LOCKED, ORDER BY height ASC)
    fetch children Abstracts (blob or node children, depending on height)
    LLM call to synthesize a single Abstract for this node
    INSERT data_node_abstracts
  commit
```

This is structurally the same long-transaction-with-FOR-UPDATE pattern
as `blob_extractor`. The conn is pinned during the LLM call; the
trade-offs are the same and are spelled out in `05.blob_extractor.md`.

`FOR UPDATE SKIP LOCKED` on the candidate row IS the claim. Parallel
workers naturally pick different unprocessed nodes — even within the
same user — because each row can only be locked once. The
implementation is thus trivially parallelisable: `concurrent_workers`
can scale up to the connection pool's cap with no additional
coordination.

## The "ready for extraction" gate

Per the spec in `04.immutable_data_pipeline.md`, `node_extractor`
only proceeds when the user's tree is settled. Checked at iteration
start:

- Every `data_files` row of type `PDF` or `TEXT` has a final blob.
- Every `data_blobs` row has a `data_blob_edges` row (in the tree).
- Every `data_nodes` row has a `data_node_weights` row (weighted).

`OTHER`-typed files are excluded from the file gate — they have no
processable content and are skipped by every pipeline worker.

The gate is **soft**: it's checked at iteration start, not held as
an invariant across the iteration. The tree can change mid-LLM-call
(e.g. `blob_extractor` lands a new file and `tree_builder` reshuffles
some edges). If that happens, our newly-INSERTed abstract is
invalidated by the edge-side trigger cascade essentially as soon as
it lands, and a future iteration recomputes it.

The alternative — holding a per-user advisory lock across the LLM
call to serialise against `tree_builder` — would prevent the wasted
work but at the cost of serialising the two workers. We pay one
wasted LLM call per disturbance instead, which dominates in the
expected workload (long stable periods after sync bursts).

## The candidate query

```sql
SELECT n.node_id, n.height
FROM data_nodes n
WHERE n.user_id = $1
  AND NOT EXISTS (
      SELECT 1 FROM data_node_abstracts a WHERE a.node_id = n.node_id
  )
  AND NOT EXISTS (
      SELECT 1 FROM data_node_edges e
      WHERE e.parent_node_id = n.node_id
        AND NOT EXISTS (
            SELECT 1 FROM data_node_abstracts a2
            WHERE a2.node_id = e.child_node_id
        )
  )
  AND (
      EXISTS (SELECT 1 FROM data_node_edges WHERE parent_node_id = n.node_id)
      OR EXISTS (SELECT 1 FROM data_blob_edges WHERE parent_node_id = n.node_id)
  )
ORDER BY n.height
LIMIT 1
FOR UPDATE SKIP LOCKED
```

The "at least one outgoing edge" guard at the end rejects orphan
candidates — a node with no children would otherwise satisfy the
vacuous "no children without abstracts" condition and trigger a
no-children error during fetch. Such a node should normally have
been collected by the deferred orphan trigger, but the guard makes
the candidate query robust against any race window.

## Prompt design

The Abstract used at the node level is the **base `Abstract`**
(from `service/abstract.py`), without a `running_summary` field —
the rolling-chain semantics don't apply to a clustered group of
unordered children. Blob abstracts use `RollingAbstract`, a subclass
that adds `running_summary` with a default of `""`, so a node
Abstract's JSON validates as a RollingAbstract if a consumer ever
wants one uniform shape.

The agent's prompt:

- **Input**: a JSON list of the children's Abstracts (either
  blob-level RollingAbstracts or node-level Abstracts; both
  serialise the same to JSON for the LLM's purposes).
- **Task**: produce one Abstract that captures what the whole
  group is collectively about, with the LLM instructed to merge
  overlapping topics rather than enumerate every child's verbatim.
- **Output**: typed as `Abstract` via `pydantic-ai`'s
  `output_type` parameter, so no JSON-parsing glue is needed.

The agent's instructions reference per-field constraints
(`summary_words`, `topics_count`) from `NodeExtractorSettings`,
matching the same pattern as `blob_extractor`. The fields evolve
independently — node summaries can be tuned differently from blob
summaries if we ever want height-aware constraints (e.g. longer
summaries near the root).

## Failure handling

Same per-worker exponential backoff as the other two workers
(5s → 5min, multiplier 2, reset on success). An exception aborts
the iteration's transaction — the in-flight LLM call's output is
lost, but no DB writes leaked — and a backoff sleep precedes the
next attempt. A persistently-failing node (e.g. an unusable
children-Abstract payload that the LLM keeps rejecting) keeps the
worker's backoff log noisy but doesn't block any other node from
being processed by a parallel worker.

There is no `data_node_failures` table. As with the other workers,
we accept indefinite retries in exchange for schema simplicity; if
in practice we hit poison-node noise that drowns out useful logs,
a small immutable failure table is the natural addition.

## Concurrency: parallel by default

`concurrent_workers` (default 1) is the number of `worker_loop`
copies in the process. Increasing it scales linearly — different
candidate rows get claimed by `FOR UPDATE SKIP LOCKED`, the LLM
calls run independently, and the only contention is the connection
pool size. Within a single user's tree, parallel workers can
process different nodes at the same height simultaneously, then
move up to the next height once that layer's abstracts are all
committed.

## What's intentionally out of scope (for now)

- **Per-height prompt specialisation.** All heights share one set
  of instructions and field-count constraints. A future
  refinement could vary the prompt by height (terser leaves,
  broader-stroke roots) — straightforward to add as a settings
  branch.
- **Re-extraction on prompt change.** Changing the agent's
  instructions doesn't invalidate existing rows. A maintenance
  pass that deletes `data_node_abstracts` for a user would force
  re-extraction; we don't have one yet because the prompt is
  stable in practice.
- **Cross-user batching.** Each LLM call is one node. Anthropic's
  batch API could amortise costs but adds complexity we don't
  need at the current scale.
