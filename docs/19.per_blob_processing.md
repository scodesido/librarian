# 19. Per-blob processing: incremental, crash-resumable blob extraction

This document records the move away from the "one file = one long
transaction" shape of `blob_extractor` (described in
`05.blob_extractor.md`) toward building a file's blob set **one blob at a
time**, with completeness and integrity guaranteed by the database rather
than by an all-at-once insert.

## The problem with the all-at-once design

The original `blob_extractor` held a single transaction open for an
entire file: download → for each chunk, two LLM calls (main + tag) →
one batched embedder call → compute the file-relative embeddings →
insert the whole blob set in reverse order. Atomicity was the point: a
file was either fully present or fully absent, and `is_final_blob` on the
tail marked "done".

In practice this had two costs:

- **A crash restarts the whole file.** A worker that dies after
  abstracting 40 of 50 blobs has committed nothing; the next iteration
  redoes all 50 LLM passes. For large files the wasted LLM spend is the
  dominant failure cost.
- **No intra-file progress.** The sync tab can only show "file ready /
  not ready"; there's no signal for "37 of 50 blobs abstracted", because
  nothing is durable until the end.

## The shape: three tables, manifest-first

```
data_files                       the root (unchanged)
  └─ data_file_manifests         1:1 — how many blobs the file SHOULD have,
     │                                 + parse-time metadata. Written first.
     └─ data_blobs               core per-blob content: abstract +
        │                              embedding_blob. Built one at a time.
        └─ data_blob_file_embeddings   1:1 — embedding_with_file, computed
                                       from the whole set, inserted atomically.
```

This mirrors the existing node side, where `data_nodes` carries two 1:1
derived tables (`data_node_weights`, `data_node_abstracts`), each with
its own worker and readiness predicate (see `04`). The blob side now has
the same split: `data_blobs` is the intrinsic per-blob content consumed
by retrieval; `data_blob_file_embeddings` is the file-relative vector
consumed only by `tree_builder`'s descent.

`is_final_blob` and `next_blob_id` are gone. The forward linked list was
write-only and could only be built end-to-beginning, which is exactly
what blocks incremental forward insertion. Ordering is carried by
`UNIQUE(file_id, file_blob_index)`; completeness is carried by the
manifest (below).

## The manifest is the denominator

`data_file_manifests.expected_blob_count` is the count the rest of the
design was missing. Chunking is deterministic — PDF chunks are fixed
page ranges, TEXT chunks fixed word groups — so the number of blobs a
file must yield is knowable as soon as the bytes are in hand, before any
LLM call. The worker writes the manifest as its **first commit**, then
fills in blobs `0 .. expected_blob_count - 1`.

The manifest is also the natural home for "metadata you can only know
once you've loaded the file": `page_count` / `char_count`, `byte_size`,
and a `content_hash` for future change-detection. Only
`expected_blob_count` is load-bearing today. Sync stays lightweight (it
just lists files); the download-and-parse that populates the manifest is
the worker's job.

## The worker loop

```
acquire pg_advisory_lock(user_id, file_id)        # session-level, not _xact_
download + parse → chunks                          # deterministic, no LLM
manifest = SELECT … FROM data_file_manifests WHERE file_id
if manifest is None:
    INSERT manifest(expected_blob_count = len(chunks), page/char/size/hash)
elif len(chunks) != manifest.expected_blob_count
     or any existing blob[i] range != chunks[i] range:     # content drifted
    DELETE FROM data_file_manifests WHERE file_id          # cascade-invalidate
    return                                                 # next visit rebuilds
for i in range(highest_present_index + 1, expected_blob_count):
    prev_running = <last committed blob's abstract.running_summary>
    abstract, embedding_blob = LLM + embed(chunks[i], prev_running)   # NO open tx
    with short_tx: INSERT data_blobs(i, …)                            # durable
if no file-embeddings exist for this file:
    with one_tx:
        ebs = SELECT embedding_blob …
        INSERT all data_blob_file_embeddings(compute_with_file(ebs))   # atomic batch
```

Key properties:

- **Session-level advisory lock, not a long transaction.** One worker
  owns a file for the duration, but each blob commits in its own short
  transaction. The connection is pinned but no transaction is held open,
  so VACUUM isn't blocked and a crash loses at most one blob's work.
  Postgres releases a session advisory lock automatically when the
  connection drops, so crash recovery stays implicit — no stale-claim
  sweeper. The lock (not a row `FOR UPDATE`, which would release between
  the short transactions) is what stops two workers from racing on the
  same file's next blob and burning duplicate LLM calls.
- **Download once per visit, commit per blob.** "One blob at a time"
  means per-blob *commit*, not per-blob *re-pick*: a visit downloads the
  file once and processes all remaining chunks. Download cost is
  unchanged from the old design; the resumability win comes from the
  per-blob commits.
- **The `running_summary` chain survives restarts.** The cross-blob
  running summary is persisted in each blob's `abstract` JSONB, so a
  resuming worker seeds the next chunk by reading it back from the last
  committed blob — no in-memory state needed.
- **The file-embedding step needs no resilience machinery.**
  `compute_with_file_embeddings` is pure arithmetic over the already-
  stored `embedding_blob` vectors — no LLM, no embedder call. So it's one
  fast atomic transaction for the whole file. A crash leaves zero rows;
  the next visit redoes it. "All file-embeddings land together" is
  achieved by doing them in one transaction, not by a constraint.

## Content drift and invalidation

If a file changes upstream, the worker's recomputed chunk list won't
match the manifest (different count) or the existing blobs (different
`file_start`/`file_end`). Either mismatch triggers **invalidation**:
`DELETE FROM data_file_manifests WHERE file_id` cascades to the blobs and
their embeddings, the file row stays, and the next visit rebuilds from a
clean slate with a fresh manifest. No fingerprint column or mutable
state is needed; determinism of chunking does the work.

This terminates as long as a file's content is stable across a single
extraction pass — which is sync's responsibility (a `source_modified_at`
change is a delete-and-resync), not `blob_extractor`'s. A file being
actively rewritten on every download would thrash, but that is bounded
by the worker's existing exponential backoff, no worse than a poison-pill
chunk under the old design. We deliberately do **not** add a retry
counter — that would reintroduce the state-machine the immutable design
removed.

## Integrity: the DB guarantees "never ready when it isn't"

The design goal is that **no sequence of writes the application could
perform — now or in some future refactor — can leave a file looking
ready when it isn't.** That guarantee lives in triggers, so it survives
code changes without code review. The invariants and their enforcers:

| Invariant | Enforced by |
|---|---|
| A blob can't exist without its manifest | FK `data_blobs.file_id → data_file_manifests` |
| Index in `[0, expected_blob_count)`, user matches | `data_blobs_check_against_manifest` (BEFORE INSERT) |
| No duplicate index | `UNIQUE(file_id, file_blob_index)` |
| Rows never mutate | `prevent_any_update` (BEFORE UPDATE) |
| **No hole ever** (incl. after deletes) | `data_blobs_check_contiguous` — `DEFERRABLE INITIALLY DEFERRED` constraint trigger: indices form a contiguous `0..k` prefix (or empty) |
| File-embeddings are all-or-`expected` | `data_blob_file_embeddings_check_all_or_none` — deferred constraint trigger |
| File-embedding rows match their blob | FK + `_check_consistency` (file_id/user_id match the blob) |

The contiguity check **must** be deferred, not row-level: during a
cascade delete the sibling rows disappear in arbitrary order, so a
per-row guard would misfire mid-statement. Evaluating the end state once
per transaction sidesteps that. Incremental growth always satisfies it;
the only state it rejects is a hole punched by an out-of-band delete of a
non-top blob — which is precisely the state that could make the
completeness probe lie.

Two readiness probes fall out, both cheap and trustworthy:

- **Blob set complete** — the blob at index `expected_blob_count - 1`
  exists. Trustworthy because contiguity forbids a hole beneath it, so
  the top index existing implies the whole `0..k` prefix exists.
- **File fully processed** — *any* `data_blob_file_embeddings` row exists
  for the file. The all-or-`expected` trigger means file-embeddings only
  ever exist as a complete set of `expected_blob_count` rows, each of
  which needs a blob; so one existing row proves the whole pipeline for
  that file is done. A single `EXISTS` is the readiness gate.

Every other deviation — a deleted blob, a deleted manifest, a crashed
half-batch — lands in the **safe** direction: the file reads as *not*
ready and the worker re-derives. The dangerous "looks ready but isn't"
direction is structurally unreachable.

## Migration and reload

The change is destructive — the split data can't be reassembled from the
old `data_blobs` (the `embedding_with_file` column moves out,
`is_final_blob` is gone) — so the migration clears `data_files` to a
fresh slate. Re-syncing from Drive repopulates under the new schema.
