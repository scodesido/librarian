# 01. Base API

This document captures the foundational decisions behind the backend HTTP API.
It explains why the API is shaped the way it is, so that subsequent additions
fit naturally into the existing structure.

## Goal

The backend exposes a small JSON HTTP API that the React frontend (and,
eventually, other clients) consume. It is the single integration point with
external services: PostgreSQL for persistent state, Google OAuth and Google
Drive for user identity and data.

The API is meant to stay deliberately small. We want each piece to be
obvious — you should be able to find any endpoint by walking the folder tree,
and read its full implementation in one screen.

## Web framework: FastAPI

We use FastAPI as the web framework. Two reasons drove the choice:

- It plays well with Pydantic, which we already use as our "structs" of choice
  across the codebase. Request and response schemas are just `BaseModel`s,
  shared with the rest of the code without any glue layer.
- Its dependency-injection model fits the way we want to share request-scoped
  resources (database connections, HTTP client, current user) without passing
  them explicitly through every function.

The app object is built by a `create()` factory in `librarian/api/app.py` and
launched by `uvicorn` from `librarian/api/main.py`. Keeping creation in a
factory lets the same app be assembled from configuration, and lets uvicorn's
`--reload` work cleanly in development.

## Folder layout maps to URL structure

API endpoints live under `librarian/api/endpoints/`. The folder hierarchy is
chosen to mirror the URL hierarchy:

```
endpoints/
  health.py            -> /health
  auth/me.py           -> /auth/me
  oauth/google.py      -> /oauth/google/...
  gdrive/files.py      -> /gdrive/files/...
```

Each terminal Python module is one router (`APIRouter`) with a small number of
related endpoints. The router's `prefix` matches its location in the tree.
Routers are wired into the app explicitly in `app.py` via `include_router` —
there is no auto-discovery. The list of mounted routers in `app.py` is the
single source of truth for what the API exposes.

This convention has two consequences we want:

- "Where is endpoint X?" is answered by looking at its URL path.
- Adding an endpoint means creating (or extending) a small file in the right
  folder, never editing a registry.

## Code locality: models live next to endpoints

Request and response models are defined in the same file as the endpoint that
uses them. Helper models for a specific feature live with that feature. We
avoid central `models.py` or `schemas.py` modules. The reasoning:

- Most models are used in one place. Sharing them across files is a yagni
  problem; when sharing is genuinely needed, we can promote at that point.
- Reading an endpoint should require reading one file, not three.

The same principle applies to small helpers used by a single endpoint.

## Configuration: layered Pydantic settings

Settings are defined as nested `BaseModel`s on a top-level `Settings` object
(`librarian/api/settings.py`), built on top of a generic `YamlSettings` base
(`librarian/settings/base.py`). Sources, in priority order, are: process
arguments, environment variables (prefixed `LIBRARIAN__`, double-underscore
nested), then YAML files.

Why this shape:

- Defaults live in code, next to the type, so the schema is self-documenting.
- YAML covers structured config that humans edit (CORS origins, scopes, URLs).
- Environment variables override individual leaves, which matches how secrets
  and per-environment toggles are injected by Docker / CI.
- Secrets are typed `SecretStr` so they don't leak into logs by accident.

Settings are instantiated once at import time (`settings = Settings()`) and
imported wherever needed.

## Resource lifecycle: lifespan + app state

Long-lived resources — the asyncpg connection pool and the aiohttp client
session — are attached to `app.state` via async context managers composed in
the FastAPI `lifespan`:

```python
async with attach_db_connection_pool(app), attach_http_client(app):
    yield
```

Each `attach_*` helper opens the resource on enter and closes it on exit.
Endpoints get the resource through a small dependency wrapper:

- `DbConnection` (`api/core/db/connect.py`) acquires a connection from the
  pool for the duration of the request.
- `HttpClient` (`api/core/http/client.py`) returns the shared aiohttp session.

Endpoints don't see the lifecycle at all; they receive a ready-to-use object
typed as a FastAPI dependency. This keeps endpoint code free of setup boilerplate
and makes lifecycle bugs (leaks, double-closes) impossible to introduce locally.

## Database access: thin Table classes, no ORM

We talk to PostgreSQL directly through asyncpg. There is no ORM. Each
database table has a small wrapper under `api/core/db/tables/`:

- A `TableModel` (Pydantic) describing the row shape.
- A `Table` subclass holding a connection and exposing a few named methods
  (`for_user`, `create`, `update_tokens`, …) — each method writes a single
  SQL statement.

The base classes (`api/core/db/table.py`) are intentionally minimal:
`TableModel.from_record` validates an asyncpg `Record` into the model, and
`Table.__init__` stores the connection. No metaclass magic, no query builder.

Why this approach:

- SQL stays visible. We can reason about indexes, transactions, and query
  plans without going through an abstraction layer.
- The wrapper exists only to give the SQL a name and a typed return. It
  pays for itself the first time a query is reused, and is cheap when it is
  not.
- Tables compose at the call site (see the OAuth callback's transaction):
  `async with conn.transaction(): ...` over multiple `Table` instances.

Migrations are managed by dbmate (see CLAUDE.md for the workflow).

## Outbound HTTP: shared aiohttp session

External calls (Google OAuth token exchange, Drive API, etc.) go through the
shared aiohttp `ClientSession` injected as `HttpClient`. A single pooled
client per process is the right default — it amortizes TCP and TLS setup
across requests and gives us one place to set timeouts and connection limits.
Pool size and timeout are configurable via `HttpClientSettings`.

## Cross-origin: CORS for the separate frontend

The frontend is served from a different origin (Vite dev server in
development, a separate static host in production). CORS is configured in
`app.py` with `allow_credentials=True` because authentication relies on
cookies (see `02.auth.md`). The list of allowed origins comes from settings
so each environment can pin its own.

## Health endpoint

`GET /health/` returns a constant `{"status": "ok"}`. Its purpose is to give
container orchestrators and uptime checks a cheap, dependency-free
liveness probe. It deliberately does not check the database — readiness
checks belong to a separate endpoint if and when we need them.
