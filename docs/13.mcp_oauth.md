# 13. MCP OAuth: per-user auth for the `/mcp` endpoint

This document describes the OAuth 2.1 authorization server that fronts
the MCP endpoint (`11.mcp.md`). It replaces the operator-pinned
`MCPSettings.user_id` knob with a real per-call user identity, so that
multiple users can each plug their Librarian library into an external
MCP client (claude.ai) without sharing a single backend account.

## Goal and shape

The MCP spec gates remote MCP servers behind OAuth 2.1. We are the
authorization server (AS) **and** the resource server (RS, the `/mcp`
endpoint). External MCP clients — claude.ai today, others later —
register dynamically, redirect the user here to consent, and receive
an opaque bearer token they present on subsequent `/mcp` calls.

Two pieces are deliberately separate:

- **Identity** comes from the existing Google OAuth flow (`02.auth.md`).
  Google answers "who is this human?". Nothing in the MCP-auth layer
  re-implements that question.
- **Authorization** is local to Librarian. We mint our own bearer tokens
  scoped to the MCP API, store them hashed, and revoke by deleting rows.
  An access token issued to claude.ai gives claude.ai permission to call
  `/mcp` on behalf of a specific user — but it carries no Google scopes
  and is not interchangeable with anything Google issued.

This is Architecture C ("we are the AS, delegating user authentication
upstream"). It keeps the MCP token strictly scoped to our API and avoids
re-using Google tokens as opaque bearers (a known anti-pattern: Google
won't dynamic-register external MCP clients, and validating its tokens
would require a userinfo call per request).

## Why the MCP SDK provider, not a hand-roll

The MCP Python SDK ships an `OAuthAuthorizationServerProvider` Protocol
plus `create_auth_routes(...)` to mount the protocol endpoints
(`/.well-known/oauth-authorization-server`, `/authorize`, `/token`,
`/register`, `/revoke`). We implement the Protocol against our tables in
`api/core/oauth/auth_server/provider.py` and let the SDK own the routing, the
PKCE check, the redirect_uri match, and the metadata document.

The SDK's seam is the return value of `authorize()`: a redirect URL. That
hands control back to us for *user authentication*. We point it at
`/oauth/mcp/continue`, which either kicks the user into the Google flow
(via `/oauth/google/login?next=...`) or — if already signed in — sends
them straight to the consent screen. This split (SDK owns the protocol,
we own the user-facing flow) is exactly the boundary we want: switching
identity providers later means changing the bridge endpoint, nothing
else.

## End-to-end flow

```
claude.ai                                          Librarian
   │
   │ 1. discover .well-known/oauth-protected-resource/mcp
   │ ─────────────────────────────────────────────────►
   │
   │ 2. discover .well-known/oauth-authorization-server
   │ ─────────────────────────────────────────────────►
   │
   │ 3. POST /register {redirect_uris, client_name, ...}
   │ ─────────────────────────────────────────────────►   oauth_clients
   │ ◄───────────────────────────────────────────────── { client_id }
   │
   │ 4. open user browser → GET /authorize?...&code_challenge=...
   │ ─────────────────────────────────────────────────►
   │                                              [SDK route]
   │                                              provider.authorize()
   │                                              → store pending grant
   │                                              → redirect to
   │                                                /oauth/mcp/continue
   │                                                          │
   │                                              No session? └► /oauth/google/login
   │                                                                │
   │                                                                ▼ (existing Google flow)
   │                                              /oauth/google/callback → set session, redirect
   │                                                                │
   │                                              /oauth/mcp/continue ── (now signed in)
   │                                                                │
   │                                              /oauth/mcp/consent (consent UI)
   │                                                                │
   │ 5. 302 to claude redirect_uri?code=<nonce>&state=...
   │ ◄─────────────────────────────────────────────────  flip grant to 'granted', attach user_id
   │
   │ 6. POST /token { code, code_verifier, redirect_uri }
   │ ─────────────────────────────────────────────────►  [SDK route]
   │                                              verify PKCE + redirect
   │                                              provider.exchange_authorization_code()
   │                                              → mint access + refresh tokens
   │                                              → mark grant 'consumed'
   │ ◄───────────────────────────────────────────────── { access_token, refresh_token, ... }
   │
   │ 7. POST /mcp  Authorization: Bearer <access_token>
   │ ─────────────────────────────────────────────────►  [Bearer middleware]
   │                                              load_access_token → user_id
   │                                              tool reads user_id from contextvar
   │                                              runs retrieval for that user
   │ ◄───────────────────────────────────────────────── { ...result... }
```

## Storage model

Four tables, all created in `202605260001_mcp_oauth.sql`:

- **`oauth_clients`**: one row per dynamically registered MCP client.
  Open registration — anyone who POSTs to `/register` gets a row. We
  store `client_name` (for the consent screen), `redirect_uris` (for the
  SDK's exact-match validation at `/authorize` and `/token`), and the
  protocol-echo fields (`grant_types`, `response_types`,
  `token_endpoint_auth_method`). We do not store the `client_secret` —
  MCP clients are public, so the secret is never used at `/token`.

- **`oauth_authorization_grants`**: one row per in-flight or recently-
  redeemed authorization code. The same row tracks both the pending-
  consent state and the post-consent state, distinguished by a `status`
  column (`pending → granted → consumed`). The PK `code` doubles as the
  nonce we hand to the user on the redirect and the eventual
  authorization code the MCP client redeems at `/token`. A CHECK
  constraint enforces that a `pending` row has no `user_id` and a
  `granted`/`consumed` row has one — making the state machine visible at
  the schema level.

- **`oauth_access_tokens`** and **`oauth_refresh_tokens`**: bearer
  tokens stored *hashed* (SHA-256, no salt; the inputs are already 32+
  bytes of `secrets.token_urlsafe` entropy). Same argument as encrypting
  Google refresh tokens at rest: a database leak should not become a
  bearer-credential leak. Both tables carry `user_id`, `client_id`,
  `scopes`, `resource`, `expires_at`.

Token lifetimes are configurable via `OAuthASSettings` and default to
30 days (access) / 90 days (refresh). Long, per the decision to use
revocable opaque tokens rather than short-lived JWTs with a refresh
dance. Revocation is one `DELETE` away. Expired rows are filtered out of
lookups; a background sweep is a later optimisation.

## The three security legs

Open dynamic client registration means anyone can register a client.
Three mechanisms keep that safe:

1. **PKCE (RFC 7636).** The SDK's `/token` handler computes
   `SHA-256(code_verifier)` and refuses the exchange unless it matches
   the `code_challenge` stashed at `/authorize` time. The verifier never
   leaves the client, so an attacker who intercepts the authorization
   code at the redirect step cannot redeem it.
2. **Strict redirect_uri matching.** The SDK validates the redirect_uri
   on `/authorize` against the URIs the client registered. Byte-for-
   byte, not a prefix. A malicious registered client cannot redirect to
   an arbitrary URL it sneaks in at authorize-time.
3. **Consent screen.** The bridge endpoint shows the user the client
   name and an Allow / Deny choice before the code is granted. Without
   consent, the grant stays in `pending` and the client never sees a
   code. Symmetric Allow/Deny buttons (no auto-primary) reduce the odds
   of a reflexive click-through.

The page is rendered as inline HTML by `/oauth/mcp/consent` with a
system-font stack and a compact card layout — chosen to read as a
security prompt, not a chrome-rich app screen, and to keep the FE SPA
out of the trust boundary for the consent step.

## Reverse-proxy notes

Librarian must own its host's root. RFC 8414 §3 and RFC 9728 pin the
AS and resource metadata at `/.well-known/oauth-authorization-server`
and `/.well-known/oauth-protected-resource/mcp` regardless of any
issuer path component — the well-known prefix is always host-rooted —
so the API cannot be mounted under a reverse-proxy path prefix. Give
it a dedicated hostname, or a non-default port on a shared hostname
(RFC 6454 treats `host:8443` as a distinct origin from `host:443`, so
the marketing site on `:443` and librarian on `:8443` coexist cleanly).

Two config knobs make HTTPS termination behind nginx work:

- `oauth_as.public_base_url` must be the public origin
  (`scheme://host[:port]`). The MCP SDK composes the advertised
  endpoint URLs as `str(issuer_url).rstrip("/") + "/authorize"` and
  friends, reading nothing from `X-Forwarded-*` (upstream issue
  [#242](https://github.com/modelcontextprotocol/python-sdk/issues/242),
  still open), so it must be configured explicitly. Per OAuth 2.1 it
  must be HTTPS for non-loopback issuers.
- `api.uvicorn_proxy_headers: true` plus a permissive
  `uvicorn_forwarded_allow_ips`. The Google callback URL is
  constructed via `request.url_for(...)` during the `/oauth/mcp/continue`
  bridge step; without trusted forwarded headers, uvicorn fills it in
  from the internal HTTP hop and we'd hand Google an
  `http://librarian-api:8000/...` callback that isn't on the registered
  list.

## What's intentionally out of scope (for now)

- **Confidential clients.** All MCP clients we expect register as public
  (`token_endpoint_auth_method=none`). The schema has room to add a
  `client_secret_hash` column later if a server-to-server client appears.
- **Multi-IdP linking.** The `auth_google` table is still the only
  identity source. The OAuth bridge endpoint redirects to Google login
  by name; replacing it would mean editing `consent.py` to call a
  different provider, not changing the OAuth layer.
- **Background token cleanup.** Expired rows linger in
  `oauth_access_tokens` / `oauth_refresh_tokens` / 
  `oauth_authorization_grants` until something deletes them. Lookups
  filter by `expires_at > now()`, so this is correctness-neutral, just
  table growth. A periodic vacuum job is a later add.
- **Scope step-up.** Today there is one scope (`mcp:read`). If we
  introduce a write-side MCP tool later, we'll grow the scope list and
  the consent screen will start showing per-scope detail.
- **Audit logging of token issuance / revocation.** The grant row's
  `status` transitions are observable in-table; a structured audit log
  would be a separate, additive concern.
