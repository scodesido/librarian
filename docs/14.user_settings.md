# 14. User settings: per-user models and API tokens

This document describes the system that moves model selection and API
tokens out of operator YAML and into per-user state, with a Settings
tab in the FE for the user to manage both. It replaces the
`*_api_token` and `*_model` fields that previously lived on
`BlobExtractorSettings`, `NodeExtractorSettings`, and `QuerySettings`.

## Goal

In dev the LLM slots all read a single `llm_api_token` SecretStr off
operator-side YAML. That doesn't survive a multi-user deployment: each
user brings their own API keys, picks their own models, and the
operator's job is just to enumerate which models are allowed and run
the workers. Three things follow:

- **Tokens are per-user, encrypted at rest.** Each slot gets its own
  row, so a user can run different providers in different slots (e.g.
  Anthropic for LLM, Voyage for embeddings) and rotate keys
  independently.
- **Models are per-user, validated against an operator whitelist.** The
  catalog lives in shared YAML; each slot lists its `allowed` options
  and the `default` to fall back on when the user has no row.
- **Token usage is recorded per call.** A ledger table grows by one row
  per LLM/embedder call (including retries), so we can later expose
  cost estimates or audit retry storms.

The ollama provider is special: it runs on the operator's own infra
(`librarian-ollama` in compose) and needs no API token. Picking
`ollama:<model>` in any slot uses the operator-side `ollama.host` and
saves the user from saving a key. That's also the default for the
embedding slot — embeddings see the most calls and "local by default"
keeps the dev loop cheap.

## Storage model

Three tables, all created in `202605290001_user_settings.sql`:

- **`user_settings`** — non-sensitive per-user state. JSONB columns
  rather than normalised rows: settings are a flexible thing and the
  set of fields will grow without warranting a migration each time.
  Today there's exactly one column, `models`, shaped by the Pydantic
  `UserModelSettings` (six slot strings). Future fields (retrieval
  tuning, UI prefs, etc.) go as additional JSONB columns on this same
  table — no joins, columns stay independent.

  No default on `models`: a missing row means "use catalog defaults",
  and the `GET /settings/me` endpoint synthesizes them. This keeps
  "the user has not touched their settings" observable in-table and
  avoids inserting a row at user-creation time.

- **`user_slot_tokens`** — encrypted per-slot tokens. Keyed by
  `(user_id, slot)` rather than `(user_id, provider)`: a user may want
  different Anthropic keys for `blob_extract` vs `retrieval` (billing
  isolation), and Voyage embeddings need their own key anyway. The FE
  defaults to "use one value for all slots" so the common case (one
  key everywhere) stays a single password input — the slot-keyed
  schema just doesn't prevent the user from diverging later.

  Encryption uses Fernet with the operator-side
  `user_tokens.encryption_key`, deliberately separate from
  `google_oauth.token_encryption_key` so the two key materials can be
  rotated independently. The plaintext never lands in the DB and is
  never returned by any API; the only readable per-slot state is
  `has_token: bool`.

  The `slot` column carries a CHECK pinning the closed vocabulary of
  six slot names at the schema level — adding a slot is a (Pydantic,
  migration) pair, same shape as today's `data_files.source`.

- **`user_token_usage`** — append-only ledger. One row per LLM /
  embedder call, including retries — retries ARE billed, and the
  ledger reflects billing reality so retry storms are visible
  separately from successful work. `prevent_any_update` keeps it
  truly append-only; the `(user_id, created_at DESC)` index supports
  the dominant read pattern ("recent usage for this user"). The
  `operation` column carries another CHECK closed vocabulary covering
  the eight call sites (see below).

  `provider` is the prefix from `"<provider>:<model>"`; kept as TEXT
  (no CHECK) so adding a provider in `service/llm.py` or
  `service/embedder.py` doesn't require a migration. The full model
  string is stored verbatim so historical rows survive catalog edits.

  Cost estimation is deliberately not in the ledger — only token
  counts. A future pricing table can derive costs as a join.

## Slots

Six slots cover every place the pipeline calls an LLM or an embedder:

| Slot                 | Used by                              | Notes |
|----------------------|--------------------------------------|-------|
| `blob_llm`           | `blob_extractor` main + tag agents   | Two agents share one slot — same model string, same token, prompt caching wins. |
| `node_llm_leaf`      | `node_extractor` height-0 agent      | Synthesises from blob Abstracts; cheap/fast model is usually enough. |
| `node_llm_internal`  | `node_extractor` height>0 agent      | Synthesises from synthesised Abstracts; a more capable model usually pays off. |
| `retrieval_llm`      | `/data/query` retrieval agent        | Walks the tree, picks blobs. |
| `extract_llm`        | `/data/query` preflight extractor    | One-shot question → search-terms distillation. |
| `embedding`          | Blob indexing + query-time scoring   | Must match across both call sites for vectors to live in the same space. |

The slot vocabulary is a `Literal` in
`common/settings/model_catalog.py`. The same names key:

- the CHECK constraint on `user_slot_tokens.slot`;
- the fields of `UserModelSettings` (the JSONB shape);
- the fields of `ModelCatalog` (operator whitelist);
- the URL parameter on `PUT/DELETE /settings/tokens/{slot}`.

Adding a slot is a four-line edit plus a migration.

## Model catalog: operator whitelist + defaults

`ModelCatalog` is the operator's say in what users can pick. One
`SlotCatalog` per slot:

```yaml
model_catalog:
  blob_llm:
    allowed:
      - { model: "anthropic:claude-haiku-4-5", label: "Claude Haiku 4.5" }
      - { model: "anthropic:claude-sonnet-4-5", label: "Claude Sonnet 4.5" }
      - { model: "ollama:llama3.2:3b", label: "Llama 3.2 3B (local)" }
    default: "anthropic:claude-haiku-4-5"
  # … five more slots …
  embedding:
    allowed:
      - { model: "ollama:qwen3-embedding:0.6b" }
      - { model: "voyageai:voyage-3.5" }
    default: "ollama:qwen3-embedding:0.6b"
```

A `model_validator` on `SlotCatalog` enforces `default ∈ allowed` —
typos in YAML fail at process startup, not at first request.

The catalog is shared infrastructure: both the `api` and `service`
processes parse identical YAML for it. We deliberately did NOT make
the service fetch the catalog from the API at boot (it'd couple
worker startup to API availability and add a network hop on cold
start) and we did NOT move the catalog into the DB (overkill for
operator-managed config). The cost is two YAML blocks that have to
stay in sync — a real problem at scale but a non-issue with two dev
files mounted from the same git tree.

The catalog has two consumers in the backend:

1. **PUT-time validation.** `endpoints/settings/me.py` rejects an
   incoming `UserModelSettings` if any slot's chosen model isn't in
   that slot's `allowed`. The shape validation (must be
   `"<provider>:<model>"`) is on `UserModelSettings` itself.
2. **Resolve-time fallback.** `ModelCatalog.resolve(slot, user_choice)`
   silently falls back to the slot's `default` when the user has no
   row or picked a model that's no longer in `allowed`. A catalog
   edit doesn't break in-flight workers — the resolver just glides
   onto the new default until the user re-saves.

The catalog has one consumer in the FE: `GET /settings/catalog`
populates the per-slot dropdowns in the Settings tab.

## Credential resolution

`service.credentials.resolve_user_credentials(conn, user_id, catalog,
ollama, user_tokens)` is the seam every worker / endpoint goes
through to turn a `user_id` into ready-to-use credentials. Two
queries (one for the settings row, one for the user's token rows),
then per slot:

1. Resolve the chosen model via `catalog.resolve(slot, user_choice)`.
2. If `requires_token(model)` (anything non-ollama), look up the
   `user_slot_tokens` row for that slot. If absent, raise
   `MissingTokenError(slot, model)`.
3. Decrypt the token with the operator's Fernet key.
4. Bundle into `ModelCreds(model, api_token, ollama_host, ollama_num_ctx)`.

All six `ModelCreds` come back as a `UserCredentials` frozen
dataclass — workers consume two or three slots, the retrieval
endpoint consumes two; building all six up-front keeps the resolver
to one round trip and leaves room for future cross-slot validation
("extract and retrieval must point at the same provider for prompt
caching to hit") as a pure function on the bundle.

Per-iteration cost is small: two SELECT queries returning a few
hundred bytes. We don't cache across iterations — each iteration
sees whatever the user most recently saved.

## Worker rotation

Each worker iteration:

1. Pick a random eligible user (`ORDER BY random() LIMIT 1`).
2. Resolve their credentials.
3. Claim work scoped to that user.
4. Build per-user agents/embedder, process, record usage, commit.

Random user picking spreads work across users so a single user with
broken credentials (and many pending files) can't starve the queue.
The next iteration's random pick is just as likely to land on someone
with valid creds.

On `MissingTokenError`, the iteration logs at info and returns
`did_work=False` — the worker sleeps the normal poll interval rather
than burning the exponential-backoff curve on what's a user-config
problem, not a system problem.

We deliberately did NOT add a per-user cooldown after N consecutive
failures. The "random pick" already amortises the cost across the
population, and adding cooldown state would mean either an in-memory
dict (lost on process restart) or another DB table (overkill).
Re-evaluate if a single broken user's tasks start dominating worker
CPU even with random picks.

The retrieval endpoint shares the same `resolve_user_credentials`
seam but surfaces `MissingTokenError` as 409 (mirroring the readiness
gate's status) with a "visit Settings to add it" message naming the
broken slot. The MCP tool, which has no HTTP-status notion, flattens
to a `ValueError` carrying the same detail so the calling LLM can
tell the user.

## Per-iteration agent construction

Agents and embedders are built fresh inside each worker iteration
(and each retrieval request), not at worker startup. Construction is
cheap (one `pydantic_ai.Agent(...)` instantiation, no network), and
per-iteration construction means a user's new model pick or token
rotation is picked up automatically on the next iteration without
restarting the worker.

The agent builders (`build_main_agent`, `build_tag_agent`,
`build_node_abstract_agent`, `build_query_agent`,
`build_extractor_agent`) all take a `(settings, creds)` pair —
`settings` for the worker's static knobs (retry budgets, abstract
budgets), `creds` for the per-user model/token.

The embedder builder (`build_embedder`) lives in `service/embedder.py`
and takes `(model, api_token, ollama_host, dimensions)` — pre-this
refactor there were two near-identical copies (one in
`blob_extractor/embed.py`, one in `retrieval/embed.py`); consolidated
because they only differed in how they unpacked the same fields off
two different settings objects.

## Token usage ledger

Eight operation kinds cover every call site:

| Operation              | Where                                                  |
|------------------------|--------------------------------------------------------|
| `blob_extract`         | `blob_extractor` main agent (one per blob)             |
| `blob_tag`             | `blob_extractor` tag classifier (one per blob)         |
| `node_extract_leaf`    | `node_extractor` height-0 agent                        |
| `node_extract_internal`| `node_extractor` height>0 agent                        |
| `retrieval`            | `/data/query` retrieval agent (one per request)        |
| `extract_search_terms` | `/data/query` preflight extractor (when it runs)       |
| `embed_blob`           | `blob_extractor` embedder (one batched call per file)  |
| `embed_query`          | `/data/query` query embedder (one per request)         |

`service.usage` carries the helpers:

- `TokenUsage` — `(input_tokens, output_tokens)` frozen dataclass
  returned by every helper that fronts an LLM/embedder call.
- `agent_usage(result)` — extracts `(input_tokens, output_tokens)`
  from a pydantic-ai `RunResult`, coercing missing fields to 0
  (some local providers leave them unset; the DB CHECK forbids
  negative).
- `record_usage(conn, user_id, operation, model, usage)` — inserts
  one row.

The Embedder protocol now returns `EmbedResult(vectors,
input_tokens)`; embedders surface the provider's input-token count
(`prompt_eval_count` for Ollama, `usage.total_tokens` for Voyage).
Embedder rows carry `output_tokens=0` by convention — embedders
don't have an "output tokens" notion.

**Failure semantics.** Worker writes happen on the same conn as the
work inside the per-iteration transaction — a rollback unwinds the
ledger row alongside the rest. API writes happen on the
implicit-autocommit conn (no enclosing transaction). If an LLM call
raises (BudgetExceededError, ModelRetry exhaustion, network),
pydantic-ai doesn't surface partial usage, so the row isn't written
and the partial tokens are unbilled. Not solvable without SDK help;
acceptable cost for the simplicity of "one row per successful call".

## API endpoints

Under `/settings/`, all auth-gated by `CurrentUser`:

```
GET    /settings/catalog              → ModelCatalog (operator whitelist)
GET    /settings/me                   → effective UserModelSettings
PUT    /settings/me                   → 204; validates against catalog
GET    /settings/tokens               → [{slot, has_token}]
PUT    /settings/tokens/{slot}        → 204; body {token}; encrypts at rest
DELETE /settings/tokens/{slot}        → 204
GET    /settings/usage?since_days=30  → aggregated UsageAggregate list
```

Endpoints live under `endpoints/settings/` mirroring the URL
structure — `me.py`, `tokens.py`, `catalog.py`, `usage.py`. The
folder is local to the user; there's no admin surface and no
`/users/{id}/` prefix.

`PUT /settings/me` is lenient on token presence: the user can save
settings before adding tokens (the FE just shows an inline warning).
Workers/retrieval surface the 409 when the model is actually used.
This split keeps the Settings page non-modal — the user can edit
piecewise without each step being blocked by the others.

`GET /settings/usage` aggregates by `(operation, provider, model)`
over a configurable window (default 30 days, hard cap 365). Sorted
by `SUM(input_tokens) DESC` so the heaviest consumers float to the
top.

## Frontend: the Settings tab

`frontend/src/settings/settings-panel.tsx` is mounted as a fourth tab
on the home screen. Three sections:

- **Tokens** — defaults to a single "Use one value for all slots"
  password input + "Apply to all slots" button, plus a per-slot
  status list (Saved / Not saved) with a Remove button per slot. The
  user can flip a switch to expand into six individual password
  inputs (each with their own Save / Remove buttons) when they
  genuinely want different tokens per slot. The default-on mode is
  the user's stated common case ("one Anthropic key for everything"),
  which the schema doesn't prevent but the UI makes frictionless.

- **Models** — one Mantine `Select` per slot, populated from the
  catalog endpoint. The current effective selection is shown. An
  inline orange warning appears under any slot whose chosen model
  requires a token the user hasn't saved — same condition as the
  workers' `MissingTokenError`. One "Save models" button at the
  bottom; PUT validates server-side too.

- **Usage** — read-only table of per-(operation, model) totals over
  the last 30 days, sorted by input tokens. Numbers are formatted
  with locale thousand-separators. No date picker yet — bring it
  back when the data needs slicing.

After every save the FE refreshes the relevant slice (`/settings/me`,
`/settings/tokens`) so the displayed state is whatever the server
just accepted (catalog fallback included).

## Migration story

There is no migration path from the old `*_api_token` fields to
`user_slot_tokens`. Operator-side tokens were dev secrets, not
production state, so the cutover is: the operator updates their YAML
to drop `*_api_token` / `*_model` / `ollama_host` / `embedding_*`
fields under each worker, adds the new `model_catalog:`,
`ollama:`, `embeddings:`, `user_tokens:` blocks, and every user
fills in their own tokens via the Settings tab on first login. Until
they do, their pipeline picks the slot defaults — typically ollama
for embedding (works out of the box) and Anthropic for LLMs (which
needs a token), so retrieval and the workers will sit idle until the
user saves a token.

## What's intentionally out of scope (for now)

- **Cost estimation.** The ledger carries raw token counts. A pricing
  table joined at read time can derive cost; not implemented because
  the dev catalog doesn't have stable pricing data yet and the FE
  doesn't ask for it.
- **Multi-key per provider.** A user has one row per slot, not "two
  Anthropic keys with key-level analytics". If a user wants billing
  isolation across slots that share a provider, they save different
  Anthropic keys on different slots — the schema supports it; the FE
  defaults make it slightly inconvenient. Re-evaluate if real users
  want this.
- **Automatic provider failover.** If a user's Anthropic key is
  expired, the worker logs and skips them — it does not fall back to
  ollama. Workers are not allowed to use credentials the user didn't
  authorise; a quiet ollama fallback would also hide the broken-key
  problem from the user.
- **Per-user cooldown on repeated failures.** Workers re-pick at
  random; a user with a broken token keeps getting picked at the
  population's average rate. Acceptable today; add cooldown if one
  user's CPU footprint starts dominating.
- **Catalog editing via API.** The catalog is YAML-only. Operators
  edit and restart. A future admin UI / DB-backed catalog is
  feasible — `ModelCatalog` is already the seam — but unmotivated
  while there's one operator.
- **Encrypted-at-rest key rotation.** Changing the Fernet key would
  invalidate every stored token. The FE / API have no "re-encrypt
  with a new key" flow today. Operators rotate by: introducing a new
  key, asking every user to re-save their tokens, then dropping the
  old key.
- **Audit log for settings changes.** Token saves / model changes
  aren't logged anywhere durable beyond the row's `updated_at`. A
  separate audit table is a later additive concern.
