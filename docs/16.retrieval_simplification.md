# 16. Retrieval simplification: slim contract, four tools, binary blobs

This document records a post-QA reshaping of the retrieval surface
described in `09.retrieval.md` and `11.mcp.md`. The mechanism (an
agent walking the abstraction tree) is unchanged; what changes is
**what we expose** — to the agent, to the API/MCP caller during the
walk, and in the final answer — plus the addition of binary blob
output. `09` remains the historical baseline; this document supersedes
its contract details where they conflict.

## Why

QA on the retrieval path surfaced three problems:

1. **The public contract leaked internals.** Progress feedback and the
   final result both carried `node_id` / `blob_id` / `file_id`, byte
   ranges, `steps`, `visited_node_ids`, and the full extraction
   Abstract. Those are implementation details we want to keep iterating
   on — exposing them turns them into a contract we'd have to preserve.
2. **Blobs were always plaintext.** PDF fragments lost their layout;
   there was no way for an API or MCP caller to ask for the original
   bytes.
3. **The agent's tool surface conflated cheap and expensive reads.**
   `expand_nodes` returned the *whole* Abstract of every child,
   including the long prose summaries, on every descent step — most of
   which the agent doesn't need to decide where to go next.

## Abstract projections: summary vs detail

The Abstract (`service/abstract.py`) is split into two disjoint
projections, defined once in `service/retrieval/projection.py`:

- **Summary** — the cheap fields shown on every listing: `title`,
  `topics`, `domains`, `intended_audience`, the entity/facet lists
  (`persons`, `organizations`, `works`, `other_entities`, `locations`,
  `time_period`, `language`), and the two tag facets (`content_tags`,
  `format_tags`).
- **Detail** — the expensive prose, fetched on demand: `summary`,
  `key_questions`, `key_claims`, and (blobs only) `running_summary`.

The two sets together cover every Abstract field, so "detail" is
exactly "everything the listing didn't already give you." The split
lives in field-list constants plus pure helpers (`summary_abstract`,
`detail_abstract`, `abstract_title`, `abstract_tags`) that project the
stored JSONB dict — no schema change, no migration.

The user-facing notion of **tags** is the concatenation of
`content_tags` + `format_tags` into one flat list (`abstract_tags`).

## Four agent tools

`expand_nodes` / `fetch_blob_contents` (two tools) become four, under a
new `service/retrieval/tools/` package (one module per tool):

| Tool | Returns | Budget |
|------|---------|--------|
| `list_children(node_refs)` | each node's children as **summary** views (title, tags, short fields, `similarity_score`, ref) | counts against descent budget |
| `node_detail(node_ref)` | the **detail** projection for one node (the prose the listing omits) | own cap, not descent budget |
| `peek_blob(blob_refs)` | plaintext content of blobs, for in-band confirmation | own cap (`max_blob_content_fetches`) |
| `list_file_blobs(blob_ref, offset)` | **summary** views of *all blobs in the same source file*, paginated | own cap |

`list_children` replaces `expand_nodes` and keeps its semantics (batch
of up to `tool_node_id_max_count` refs, one step). The seed inlined in
the agent's instructions uses the same summary projection, so "what the
root gives you" and "what `list_children` gives you" are identical.

`node_detail` is the on-demand deepening: the agent calls it when a
node's summary is promising but it wants the prose before descending.

`list_file_blobs` exists because tree adjacency ≠ document adjacency: a
blob reached by descent has siblings *in its source file* that may live
in unrelated subtrees. The tool answers "what else is in this
document?" Because a file can hold many blobs, it is **paginated**:
`offset` plus a page size of `QuerySettings.file_blobs_page_size`
(default 20), returning the page plus a total count so the agent can
decide whether to page again. Its description tells the agent to reach
for it after peeking a blob it likes.

The prefixed-ref discipline (`n:` / `b:`) from `09` is unchanged: tools
take refs, integer ids are for logs, and a mismatched prefix is a
`ModelRetry`. The per-request caps for `node_detail`, `peek_blob`, and
`list_file_blobs` are tracked as separate counters on `QueryDeps`,
mirroring how `content_fetch_count` already bounds peeking; only
`list_children` consumes the descent budget.

## Slim user-facing surface

The agent's internal vocabulary stays internal. Two *separate*
surfaces get stripped to title + tags.

### Progress feedback

The per-tool SSE events and the MCP `report_progress` lines collapse to
a single `ProgressEvent`:

```python
class Brief(BaseModel):
    title: str | None
    tags: list[str]

class ProgressEvent(BaseModel):
    kind: Literal["progress"] = "progress"
    action: Literal["descend", "detail", "peek", "file"]
    items: list[Brief]
    step: int | None = None     # descend only
    budget: int | None = None   # descend only
```

Every tool call emits one `ProgressEvent` carrying only the title+tags
of the thing(s) it just touched. No node/blob ids, no child dumps, no
similarity scores on the wire. `step`/`budget` survive on `descend`
only — they're a progress count, not a mechanism detail. `TermsEvent`
(the distilled search string) is unchanged.

### Final result

`DoneEvent`, the JSON `QueryResponse`, and the MCP result all collapse
to a rationale plus a list of blobs:

```python
class ResultBlob(BaseModel):
    title: str | None
    file_name: str
    tags: list[str]
    mime_type: str
    content: str                 # plaintext, or base64 when encoding == "base64"
    encoding: Literal["text", "base64"]
```

Gone: `visited_node_ids`, `steps`, and per-blob `blob_id`, `file_id`,
`file_start`, `file_end`, and the full Abstract. `file_name` stays — it
is a real-world locator (which document this came from), useful to API
callers, not an internal id. `title` stays for display.

`file_name` is the file's human-readable full folder path, captured at
sync time into `data_files.name` (the `path` column holds the opaque Drive
file id — the sync key and download handle — which is not exposed). Files
synced before that column existed read back as the empty string; resolution
never blocks on a missing name.
`effective_search_terms` stays on the result: it is part of the input
contract ("this is the string I actually searched, since you left
`search_terms` blank").

## Binary blobs

Both the API and MCP gain an opt-in for original bytes instead of
extracted text. The webapp always uses text.

- **Request.** API `QueryRequest.content_format: "text" | "binary"`
  (default `"text"`); MCP `query_library(..., binary: bool = False)`.
- **Provider.** `BlobContentProvider` grows
  `fetch_bytes(blob) -> tuple[bytes, str]` (bytes + MIME):
  - `TEXT`: the `[file_start, file_end)` character slice, re-encoded
    UTF-8, `text/plain`.
  - `PDF`: ranges are *page* indices, so we reconstruct a standalone
    PDF of `[file_start, file_end)` with `pypdf.PdfWriter`
    (`extract_pdf_pages_bytes`), `application/pdf`. A blob stays a
    *fragment* — we return the page range, not the whole source file.
  - Peeking (`peek_blob`) is always text; binary only affects the final
    returned blobs.
- **Wire encoding.**
  - **API (JSON).** Structured `ResultBlob`: text mode sets
    `content`=plaintext, `encoding="text"`; binary mode sets
    `content`=base64, `encoding="base64"`, with `mime_type`.
  - **MCP.** Uniform **content-block** return in both modes (the
    natural MCP shape), because binary bytes cannot live inside MCP
    structured output. The tool returns an ordered list: a leading
    `TextContent` (rationale + effective terms), then per blob a pair —
    a `TextContent` with that blob's title + tags (JSON), followed by
    the content block: `TextContent` in text mode, or an
    `EmbeddedResource`/`BlobResourceContents` (base64 + `mimeType`) in
    binary mode. Each blob's metadata stays adjacent to its bytes. The
    embedded resource's `uri` is synthetic and non-identifying
    (`librarian://result/<index>`) so no internal id leaks. The old
    structured `MCPQueryResult` is retired.

## Out of scope / unchanged

- Pre-flight (readiness gate, search-term extraction, embedding),
  budget/backtracking math, sibling similarity scoring, prompt caching,
  and the provider dispatch all behave as in `09`.
- The tree-explorer endpoint (`/data/tree`) keeps the full `ChildView`
  with complete Abstracts — it is a browse surface, not the retrieval
  contract, and is deliberately left untouched.
