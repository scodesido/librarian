# 09. Retrieval: agent-driven walk down the abstraction tree

This document describes the `/data/query` endpoint, which answers a
user's free-form question by walking the per-user abstraction tree
(`04.immutable_data_pipeline.md`) with a `pydantic-ai` agent and
returning the most relevant blobs as plaintext. It is the first
read-side use of the schema beyond the tree-explorer endpoint.

## Goal

The pipeline produces a tree where every node carries an LLM-generated
Abstract synthesising its subtree. The top-level abstract is broad,
each level down is more specific, and the leaves are blobs of real
source documents. Retrieval is the dual of construction: at every
level, pick the children whose Abstracts best match the user's
question; descend; repeat until reaching blobs; return the best ones.

We do this with an LLM agent rather than a fixed algorithm because:

- The matching at each level is semantic, not metric. The geometry
  built by `tree_builder` (centroids on
  `embedding_with_file`) is biased toward grouping blobs of the same
  source — useful for construction, not directly for retrieval.
- The agent can backtrack. If a chosen subtree turns out to be a
  weaker match than its siblings looked, the agent can spend its
  remaining budget on a different branch. A fixed beam-search shape
  would need that logic encoded explicitly.
- The Abstract carries a rich set of fields (topics, key_questions,
  key_claims, entities, ...) — much more than a single vector. An LLM
  reading them as JSON is the natural way to use that breadth.

## Endpoint shape

```
POST /data/query           → JSON QueryResponse
POST /data/query/stream    → text/event-stream of QueryEvent
```

The streaming variant exists for the UI's exploration trace: as the
agent descends, every `expand_nodes` call emits one event, every
`fetch_blob_contents` call emits one event, and the final answer
arrives as a `done` event. The JSON variant skips the trace and only
returns the final answer; it's there for clients that just want the
answer.

Both variants take the same body:

```python
class QueryRequest(BaseModel):
    question: str   # validated <= settings.query.question_max_chars
```

Why POST for the streaming variant when SSE traditionally rides GET?
The question can be long (up to `question_max_chars`, default 1000),
and stuffing it into a URL feels wrong. The FE reads the SSE via
`fetch` + `ReadableStream` instead of `EventSource`, which is a few
extra lines on the FE side but means we keep one consistent request
shape.

## Pre-flight: readiness gate

The agent assumes a fully-built tree (every node has an abstract). If
that isn't true, the endpoint returns **409 Conflict** before
touching the LLM. The check reuses `count_user_pipeline` from
`db/readiness.py`:

```
files_total > 0
files_ready == files_total
blobs_total > 0
blobs_in_tree == blobs_total
nodes_total > 0
nodes_abstracted == nodes_total
```

The detail string identifies which gate failed (e.g. "Tree still
building (12/18 blobs attached). Wait for tree_builder to finish."), so
the FE can show the user actionable feedback instead of a generic
"not ready."

The gate is **soft**: it's only checked at request entry. The tree
can change mid-query (e.g. `tree_builder` lands a new blob and
collapses a leaf the agent was descending into); in that case the
agent's `expand_nodes` call returns the new structure and the agent
adapts. Worst case it wastes some budget on now-stale node_ids. We
accept the waste over the alternative of holding a per-user advisory
lock across the LLM call.

## Two tools, one structured output

The agent has two PydanticAI tools:

- `expand_nodes(node_refs: list[str]) -> list[ExpandedNode]` —
  fetches the immediate children of each referenced node. Each child
  carries its Abstract plus the refs the agent will need for the next
  step. The tool enforces:
  - `len(node_refs) <= QuerySettings.tool_node_id_max_count` (default 3).
  - Each ref parses as a node ref (`n:NNN`); a `b:...` ref is rejected
    with a diagnostic message telling the agent to use
    `fetch_blob_contents` instead.
  - All node ids belong to the requesting user (the same
    `WHERE user_id = ...` filter the rest of the codebase carries).
  - `step_count < budget` — see "Budget" below.
- `fetch_blob_contents(blob_refs: list[str]) -> list[BlobResult]` —
  materialises plaintext for a set of blobs via the per-source
  provider. Same ref-prefix discipline: `n:...` refs are rejected with
  a diagnostic. The agent calls this when it's at the blob layer and
  wants to confirm relevance before committing to a final selection.
  Capped at `QuerySettings.max_blob_content_fetches` total calls per
  query (defensive; the agent should not need many).

### Why prefixed string refs, not integer ids

`data_nodes` and `data_blobs` use independent BIGSERIAL sequences, so
the integer `172` can be a valid node id **and** a valid blob id at
the same time. An LLM that picks a child entry and reads "id 172"
without paying close attention to the `kind` discriminator can hand
the wrong one to a tool — and we saw exactly this in early dogfooding.

The fix is to make the type *part of the value*: every child entry
carries a `ref` field, an opaque string starting with `n:` or `b:`.
Tools accept ref lists and validate the prefix. The integer
`node_id` / `blob_id` fields remain on the views (the FE renders from
them, and they're useful for log readability), but the agent is told
explicitly in its instructions to pass `ref` verbatim and never to
construct refs by hand. A mismatched prefix is recoverable: the tool
raises a `ModelRetry` whose message names the right tool for the
ref's kind, and pydantic-ai surfaces that message to the agent for
the next turn.

The agent's structured output (`output_type=FinalAnswer`) carries the
chosen `blob_refs` (each starting with `b:`, up to `max_returned_blobs`)
plus a short `rationale`. The endpoint parses the refs back to
integer blob_ids, truncates if the agent returned more than the cap,
re-resolves them through the provider (the per-request download cache
makes the duplicate cheap), and returns the result. A non-`b:` ref in
the final answer is treated as an agent bug (502 to the client) —
unlike the in-loop ModelRetry path, the structured output isn't a
place for the agent to "correct itself" without an extra round-trip
we'd rather not pay.

Tool errors that are recoverable (bad input, unknown id, fetch cap
reached) are raised as `pydantic_ai.ModelRetry`; pydantic-ai surfaces
the message to the agent and lets it correct course. Budget
exhaustion is a hard `BudgetExceededError` that propagates past the
agent loop — per spec, that's a client-facing 400.

## Budget and backtracking

The descent budget is:

```
budget = max(2, ceil(C * (root.height + 1)))
```

where `C = QuerySettings.descent_budget_multiplier` (default 3.0).

The `+1` handles the trivial height-0 case where the whole library
fits as blob children under a single root — without it the budget
would be 0 and the agent couldn't make a single `expand_nodes` call.
The floor of 2 guarantees at least one descent and one revisit for
any tree.

The multiplier is deliberately bigger than 1: the agent is **told it
can backtrack**, i.e. re-expand a node from earlier in the
exploration if it decides a different branch looks more promising.
The extra slack on top of straight-line descent (which would only
need `root.height` calls) is what funds those revisits. With C=3 and
a height-3 tree, the agent has 12 calls — enough to descend three
parallel branches with one revisit each, or one branch with deeper
exploration.

`fetch_blob_contents` does **not** count against the budget. The
descent budget is about "how much of the tree did you explore?"; the
content-fetch cap is a separate, larger ceiling on the cost of
peeking at blob contents.

## Per-request agent, instructions carry the seed

The agent is built **per request**. The instructions string is
assembled from:

- A static preamble explaining the two tools, the budget, the cap on
  the final answer, and the backtracking allowance.
- The library's seed: the root's Abstract and the Abstracts of the
  root's immediate children, serialised as JSON.

The seed lives inside the instructions, not as a prelude tool call,
so the agent always starts with one expansion already in hand. The
seed is also stable across queries from the same user (until the
tree changes), which lets us turn on Anthropic prompt caching:

- The builder in `service/llm.py` takes a `cache_instructions: bool`
  flag.
- For `anthropic:...` models it returns an
  `AnthropicModelSettings(anthropic_cache_instructions=True)`; the SDK
  marks the instructions block with a cache breakpoint and Anthropic
  serves subsequent requests with the same instructions prefix from
  cache (5-minute TTL by default).
- For `ollama:...` (or any non-Anthropic) the flag is a no-op; ollama
  has no equivalent.

The cache key is implicit (prompt-prefix match). When the tree
changes, the seed JSON changes, the cache prefix changes, the next
request pays a fresh write — no explicit invalidation needed.

## Blob contents: a provider Protocol, GDrive-only today

The tree was built once from Drive; retrieval needs to re-materialise
blob plaintext on demand, because raw blob text is **not** persisted.
(The blob's embedding, Abstract, and source-range are stored; the
text is recomputed by downloading the source and slicing the
recorded `[file_start, file_end)` range.)

```python
class BlobContentProvider(Protocol):
    async def fetch_text(self, blob: BlobLocator) -> str: ...
```

Today the only implementation is `GDriveBlobProvider`. It holds the
user's Drive access token (resolved once per request via
`access_token_for_user`) and a per-request `dict[file_id, bytes]`
cache, so two blobs from the same file share a single download.
Slicing rules:

- `PDF`: pages `[file_start, file_end)` extracted via
  `extract_pdf_pages_text` (same pypdf path the embedder uses).
- `TEXT`: characters `[file_start, file_end)` of UTF-8-decoded
  bytes.

The dispatch lives in `build_blob_provider(source, ...)` which
branches on the `data_files.source` string. Today the only branch is
GDRIVE; the Protocol seam is here so a future provider (Notion, S3,
…) plugs in without touching the agent or endpoint.

The agent itself never sees the provider — only the
`fetch_blob_contents` tool does. The contract between the agent and
the tool is "blob_ids in, plaintext + metadata out."

## SSE format and lifecycle

The streaming endpoint emits one of four event types:

- `expand` — one per `expand_nodes` call. Carries `step`, `budget`,
  the requested `node_ids`, and the full expanded result (so the UI
  can render the children's topics inline).
- `fetch` — one per `fetch_blob_contents` call. Carries only the
  `blob_ids` it touched; the content itself isn't streamed (could be
  large, and the FE doesn't need it until `done`).
- `done` — final answer: the resolved `BlobResult`s, `visited_node_ids`,
  `steps`, and the agent's `rationale`.
- `error` — a single error message and the stream ends. Today this
  fires on `BudgetExceededError`, on unhandled exceptions inside the
  agent loop, and on the readiness-gate failures (when the SSE
  pre-flight catches them before starting the agent).

Heartbeat comments (`: heartbeat\n\n`) are sent every
`QuerySettings.sse_heartbeat_seconds` between real events to keep
intermediaries from timing the connection out.

The stream runs the agent in an `asyncio.create_task`, pushing events
through an `asyncio.Queue`. The generator yields from the queue
until it receives a `None` sentinel, then exits. Cancellation of the
streaming response cancels the agent task.

The streaming generator owns its own pool connection (via
`pool.acquire()` inside the generator) rather than reusing the
request-scoped one — the request handler returns before the
generator finishes draining, so a shorter-lived dep would already be
gone.

## What's intentionally out of scope (for now)

- **Binary blob contents.** PDF blobs are extracted as plaintext via
  pypdf, losing charts and layout. The user-facing spec calls this
  out as a "we'll work on potentially returning binary later" item.
  The Protocol returns `str` today; growing it to a `BlobContent`
  variant with optional bytes is straightforward when we need it.
- **Cross-user / shared trees.** Every query is per-user. No
  cross-user fanout exists in the schema (`04.immutable_data_pipeline.md`).
- **Streaming the agent's tokens.** We stream tool-call granularity
  (one event per `expand_nodes` / `fetch_blob_contents`), not LLM
  tokens. Pydantic-ai exposes `agent.run_stream` for token-level
  streaming, but the per-tool granularity is what the UI actually
  shows.
- **Caching across users.** Each user's seed is distinct, so the
  Anthropic prompt cache only helps within one user's requests.
  Cross-user caching would require a shared prefix the agent can use
  before adding the user-specific seed — possible but currently
  unmotivated.
- **Re-rank / fusion.** The agent's final list is taken as-is. A
  classical reranker on top is straightforward to add as a post-step
  if quality demands it.
- **Failure recovery on Drive 401.** Today an expired/revoked Drive
  token surfaces as an unhandled exception → `error` event → 500/SSE.
  When we hit this in practice the natural addition is a refresh
  retry on `access_token_for_user`; for now we let the user re-auth
  and try again.
