# 15. User worker events: surfacing background-worker outcomes

This document describes the system that records, exposes, and displays
per-user messages emitted by the **background workers** — errors, so a
user can tell *why* their pipeline is stalled, and a few clean success
milestones, so they can tell *when* it has finished. It is designed as a
general per-user event ledger that future notifications can reuse.

It builds directly on the per-user-token system (`14.user_settings.md`):
once each user brings their own API keys and model picks, the failure
modes are per-user (a missing token, an expired key, a provider rate
limit on *that user's* account) and there was previously nowhere to see
them except the operator's process logs. This system gives the user that
window.

## Goal

The three background workers — `blob_extractor`, `node_extractor`,
`tree_builder` — run detached from any request. When one of them can't
make progress for a user (their Anthropic key is missing, Drive auth
expired, the provider is rate-limiting them), today the only trace is a
`logger.exception` / `logger.info` line in the operator's logs. The user
sees a pipeline that simply never advances, with no explanation. And
when it *does* finish, there's no positive confirmation either.

We want:

- **Events recorded per user, durably** — failures the moment a worker
  hits them, plus a couple of coarse success milestones.
- **A read API** for the most recent events and for counts grouped by
  code, scoped to the current user.
- **A display on the Sync tab**, where the user already watches pipeline
  progress, that turns "stuck and silent" into "stuck because you
  haven't added an embedding token — fix it in Settings", and "building"
  into "your library is ready".

### Why "worker" events specifically

The synchronous paths already surface their own errors inline and need
no ledger:

- `/data/query` (retrieval + preflight) returns a **409** naming the
  broken slot (see `14.user_settings.md`, "Worker rotation") — the user
  sees it in the same request.
- `/data/files/sync` / `rebuild-tree` / `clear` return their error in
  the response body, which the Sync panel already renders as
  `actionError`.

The background workers are the only backend processing the user has *no*
window into. Scoping this ledger to the three workers is what the name
`user_worker_events` records: it is the workers' channel for telling a
specific user what happened on their behalf.

## The non-obvious constraint: match the event's fate to the work's

This is the decision that shapes the recording seam. The token-usage
ledger (doc 14) writes `record_usage` on the **same connection and
transaction** as the work, so a rollback unwinds the usage row with the
work — usage is only billed for work that committed. Worker events need
*two* behaviours, depending on whether the event accompanies a success
or a failure:

- **Success events ride the work transaction.** A file is "processed"
  iff its blobs committed; the event should commit atomically with them.
  So `file_processed` / `library_abstracted` are recorded on the **work
  `conn`, inside the work transaction** — exactly like `record_usage`. A
  rollback correctly takes the success event with it.

- **Failure events must survive the rollback.** The interesting failures
  *roll the work transaction back*. If the event rode that transaction
  it would vanish exactly when there's something to record. So the
  failure path records on a **fresh pool connection** that commits
  independently of the doomed work transaction.

Concretely, in a worker iteration (`blob_extractor/worker.py`,
`node_extractor/worker.py`):

```python
async def run_one_iteration(pool, http):
    async with pool.acquire() as conn:
        async with conn.transaction():
            user_id = await pick_user(conn)         # user_id known only here, inside the txn
            if user_id is None:
                return False
            try:
                creds = await resolve_user_credentials(...)
            except MissingTokenError as exc:
                await record_event(conn, user_id, EventCode.MISSING_TOKEN, ...)   # (a)
                return False                          # txn commits (empty + the event)
            try:
                ... do work ...
                await record_event(conn, user_id, EventCode.FILE_PROCESSED, ...)  # (b) success, same txn
            except Exception as exc:                  # (c) work rolled back
                async with pool.acquire() as ev_conn: # fresh conn, independent commit
                    await record_event(ev_conn, user_id, classify_exception(exc), ...)
                raise                                 # re-raise: worker_loop backoff unchanged
```

Three cases, and the connection choice falls out of each:

- **(a) Caught-inside failures** (`MissingTokenError`,
  `NoGoogleAuthError`): `user_id` is in scope and there is *no* rollback
  — the iteration returns `False` and the transaction commits empty. So
  recording on the **work `conn`** is correct and the event commits.
- **(b) Success milestones**: recorded on the **work `conn`** inside the
  transaction, committing with the work.
- **(c) Propagated failures**: the work transaction is unwinding, so we
  acquire a **fresh pool connection**, record there, then **re-raise** so
  `worker_loop`'s exponential backoff is untouched.

`record_event(conn, ...)` thus mirrors `record_usage(conn, ...)`'s
signature; the only subtlety is that case (c) hands it a *different*
connection than the one being rolled back. That single fresh-connection
acquire is the whole "survive the rollback" mechanism.

## Classification: four code bands

Events carry an integer `code`. The thousands digit is the **category**;
the full code is the granular reason. Four bands:

| Band   | Category         | Meaning                                                              |
|--------|------------------|----------------------------------------------------------------------|
| `1xxx` | informational    | Successful / progress milestones (file processed, library ready).    |
| `2xxx` | internal         | Our bug or invariant violation — unexpected exceptions, `ProcessFileError`. |
| `3xxx` | external provider| Transient provider-side failure the user can only wait out — rate limits, 5xx, timeouts. |
| `4xxx` | user-actionable  | The user can fix this from the Settings tab — missing token, invalid/expired key, lapsed Drive auth. |

The `4xxx` band is the reason this feature exists. In the per-user-token
world the dominant failure is "the user hasn't finished setting up", and
that's distinct from both our bugs (`2xxx`) and a provider being down
(`3xxx`): only `4xxx` events get a "Fix in Settings →" affordance in the
UI. Folding them into `3xxx` would lose that signal.

The closed vocabulary is an `IntEnum` (`EventCode`) in the table module,
mirroring how `Operation` is a `Literal` on `UserTokenUsage`. Both
`service` (writer) and `api` (reader / labeller) import it, the same way
both import `UserTokenUsage` today. The category is `code // 1000` — a
pure function, no separate `level`/`severity` column.

Representative v1 codes (the set will grow):

| Code   | Name                  | Source / condition                                            |
|--------|-----------------------|---------------------------------------------------------------|
| `1001` | `file_processed`      | `blob_extractor` finished a file's blobs (one per file).      |
| `1002` | `library_abstracted`  | `node_extractor` wrote the **root** node's abstract — the library is queryable. |
| `2001` | `internal_error`      | Any unrecognised exception (the classifier's default).        |
| `2002` | `pipeline_error`      | `ProcessFileError` — zero chunks, unsupported type, bad PDF mode. |
| `3001` | `provider_rate_limited` | Provider 429.                                               |
| `3002` | `provider_unavailable`  | Provider 5xx / network / timeout.                           |
| `4001` | `missing_token`       | `MissingTokenError` — no token saved for a slot.              |
| `4002` | `invalid_token`       | Provider 401/403 — key wrong or expired.                      |
| `4003` | `missing_google_auth` | `NoGoogleAuthError` — Drive auth absent/lapsed.               |

**Classification is best-effort and honest about it.** A
`classify_exception(exc) -> EventCode` helper maps the *typed* exceptions
we own (`MissingTokenError`, `NoGoogleAuthError`, `ProcessFileError`)
precisely. Provider failures arrive wrapped by pydantic-ai / the SDKs;
where we can read an HTTP status off the wrapped cause we map
429/401/5xx to their codes, and **everything unrecognised falls back to
`2001 internal_error`**. We never guess a `4xxx` from an unknown
exception — misclassifying a bug as "your fault, fix it in Settings"
would be worse than the generic internal-error bucket.

### A deliberate schema property: range CHECK, not IN-list

`code` is constrained by a **range** CHECK (`BETWEEN 1000 AND 4999`),
not an `IN (...)` list. Adding a new code is therefore a pure
`EventCode` enum edit with **no migration** — the band is reserved at the
schema level and the enum is the source of truth for which codes within
it are live. This is intentionally looser than `user_token_usage.operation`
(an `IN`-list CHECK), because event codes will accrete faster than
operations and most additions are within an existing band. `source`,
which has a small fixed vocabulary, keeps the `IN`-list CHECK.

## Volume: append-only, with throttling as a per-call policy

The ledger is **append-only** (`prevent_any_update` trigger, same as
`user_token_usage` and the immutable data tables) — it keeps full
history, which is what makes the milestone timeline and any future
notification feed possible.

But append-only collides with the worker rotation design. Doc 14 is
explicit: workers pick users `ORDER BY random() LIMIT 1` with **no
per-user cooldown**, on the reasoning that random picking amortises a
broken user's cost across the population. The consequence here: a user
with a missing embedding token raises `MissingTokenError` on *every*
iteration that happens to pick them — and a naive "one row per
occurrence" ledger fills with thousands of identical `4001` rows within
minutes.

The fix stays true to the repo's instinct ("throttle at write rather
than carry cooldown state"), but the throttle is a **per-call policy**,
not a blanket rule — because the right key differs by event kind:

- **Recurring failures** (`4001`, `3001`, …) throttle on
  `(user_id, code, source)`: before inserting, `record_event` skips if
  an identical such row exists within `throttle_window` (an operator
  setting, default ~10 min). One cheap indexed `SELECT` on the
  `(user_id, created_at DESC)` index gates the write. The ledger then
  carries "this problem recurred", not 4 000 copies — while still
  emitting a fresh row once the window lapses, so a *persistently* broken
  setup stays visibly recent.
- **Per-unit milestones** (`1001 file_processed`) do **not** throttle:
  each file is a distinct event, and a `(user, code, source)` throttle
  would wrongly collapse "file A done" and "file B done" into one. They
  always insert.
- **State milestones** (`1002 library_abstracted`) *do* throttle on
  `(user_id, code, source)`: the root abstract is recomputed every time
  the tree changes (the `invalidate_parents` triggers), so during an
  active sync it would otherwise fire repeatedly. Throttling collapses
  the burst into one "library ready" per window.

So `record_event` takes a `throttle_window: float | None` — `None` means
"always insert" (milestones like `1001`), a value means "dedup on
`(user, code, source)` within this window" (failures and `1002`). The
policy lives at the call site, where the event's semantics are known.

We considered **upserted status rows** (one row per active
`(user_id, code, source)` with `first_seen` / `last_seen` /
`occurrence_count`). It dedups for free and answers "what is *currently*
wrong" elegantly — but it is no longer a ledger, loses history, and
can't carry the milestone timeline. The throttled append-only ledger
keeps both properties at the cost of one gating `SELECT` per throttled
write. We chose history.

## Storage model

One table, created in `202606020001_user_errors.sql` (the migration file
predates this naming; the table inside it is `user_worker_events`):

```sql
CREATE TABLE user_worker_events (
    event_id    BIGSERIAL PRIMARY KEY,
    user_id     BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    code        INT NOT NULL CHECK (code BETWEEN 1000 AND 4999),
    source      TEXT NOT NULL CHECK (source IN (
                    'blob_extractor',
                    'node_extractor',
                    'tree_builder'
                )),
    detail      TEXT,
    context     JSONB,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_user_worker_events_user_id_created_at
    ON user_worker_events (user_id, created_at DESC);

CREATE TRIGGER user_worker_events_prevent_any_update
    BEFORE UPDATE ON user_worker_events
    FOR EACH ROW EXECUTE FUNCTION prevent_any_update();
```

- **`code`** — the `EventCode` value; range CHECK as discussed.
- **`source`** — which worker emitted it; small `IN`-list vocabulary,
  CHECK-pinned (adding a worker is a Pydantic + migration pair, same
  shape as `data_files.source`).
- **`detail`** — human-readable message: the exception string, the slot
  name, "Processed report.pdf (12 blobs)". Nullable.
- **`context`** — optional structured extras (`{slot, provider,
  file_id, http_status, node_id}`), JSONB for the same "grow without a
  migration" reason `user_settings.models` is JSONB. The read API passes
  it through verbatim; the FE reads known keys opportunistically.
- The `(user_id, created_at DESC)` index serves the dominant read
  ("this user's most recent events") and the throttle's pre-write lookup.

The table module `db/tables/user_worker_events.py` follows the
`UserTokenUsage` shape: an `EventCode` `IntEnum`, a `Source` `Literal`, a
`UserWorkerEventModel(TableModel)`, an `EventCountModel` for the grouped
read, and a `UserWorkerEvents(Table)` with `insert` / `recent` /
`counts` / `exists_recent` (the throttle's lookup).

## Service helpers

`service/events.py`, the analog of `service/usage.py`:

- `record_event(conn, user_id, code, source, detail=None, context=None,
  throttle_window=None)` — if `throttle_window` is set and an identical
  `(user_id, code, source)` row exists within it, skip; otherwise insert.
  Takes a `conn` (matching `record_usage`); the caller chooses which
  connection per the "match the event's fate to the work's" rule above —
  the work `conn` for success and caught-failure paths, a fresh pool
  connection for the rolled-back propagated-failure path.
- `classify_exception(exc) -> EventCode` — maps owned exception types to
  precise codes, reads provider HTTP status where available, defaults to
  `2001 internal_error`.

Worker integration, per worker:

- **`blob_extractor`** — `record_event(conn, …, FILE_PROCESSED)` after
  `process_file` returns (replacing/augmenting the existing "file done"
  log); `MissingTokenError` / `NoGoogleAuthError` caught-path events; the
  propagated-exception wrapper.
- **`node_extractor`** — `record_event(conn, …, LIBRARY_ABSTRACTED,
  throttle_window=…)` when `process_one_node` writes the **root** node's
  abstract; `MissingTokenError` caught-path; the propagated wrapper.
- **`tree_builder`** — no `resolve_user_credentials` step (pure DB
  work), so only the propagated-exception path; its `user_id` is in
  scope inside `run_one_iteration` the same way.

## API endpoints

A new top-level router, `endpoints/messages/`, parallel to
`endpoints/settings/` and `endpoints/data/`. It is cross-cutting (it
reports on all three workers) and belongs to neither the settings subtree
nor the data subtree, so it gets its own prefix. All auth-gated by
`CurrentUser`, mirroring `/settings/usage`:

```
GET /messages/recent?since_days=30&limit=50&category=4   → newest-first list
GET /messages/counts?since_days=30                       → counts grouped by code
```

- **`/messages/recent`** — `UserWorkerEventModel` list, newest first.
  `since_days` (default 30, hard cap 365, same defensive cap as
  `/settings/usage`), `limit` (default 50, cap ~200), optional
  `category` filter (`1`–`4`) translating to a `code BETWEEN
  category*1000 AND category*1000+999` predicate.
- **`/messages/counts`** — `GROUP BY code` over the window →
  `[{code, category, count, latest_at}]`, so the FE can render per-band
  badges and a per-code breakdown without pulling every row.

Request/response models live in their endpoint files (`recent.py`,
`counts.py`), per the repo's "define where you use" rule; the row and
count models live in the table module since both endpoints share them.

## Frontend: a section on the Sync tab

`frontend/src/home/worker-events.tsx` (`WorkerEvents` component) mounts
inside the existing Sync tab, beneath the pipeline-progress bars where
the user already looks to see why nothing is happening.

- **Counts row** — one badge per non-empty band: green for `1xxx`,
  yellow for `3xxx`, red for `2xxx` / `4xxx`. Driven by
  `/messages/counts`.
- **Recent list** — expandable, from `/messages/recent`: timestamp,
  source, the human `detail`. `4xxx` rows carry a "Fix in Settings →"
  link to the Settings tab; `3xxx` read as "provider issue, will retry";
  `2xxx` as "something went wrong on our side"; `1xxx` confirm progress.

Data is **fetched on mount and polled** (~10 s), not streamed. The live
pipeline counts justify their SSE stream because they tick continuously;
events are episodic and a short poll is enough machinery. Polling reuses
the `api()` client like the action buttons, rather than `EventSource`.

Per the FE conventions, styling lives in the component definition, and
the file is `worker-events.tsx` declaring `WorkerEvents`.

## What's intentionally out of scope (for now)

- **Fine-grained `1xxx` notifications.** v1 records exactly two
  milestones — `file_processed` (per file) and `library_abstracted`
  (root abstract written). Anything finer (per-blob, per-node) would
  flood the ledger and duplicate what `user_token_usage` already
  records; deferred until a concrete surface needs it.
- **Read / dismiss / acknowledge state.** A strict append-only ledger
  has no "mark resolved" or unread-badge state. Adding it means either a
  separate `user_worker_event_acks` table or abandoning append-only.
  v1 shows "recent" + "counts" only; revisit if users want to clear
  notifications.
- **Retention / pruning.** The ledger grows unbounded, exactly like
  `user_token_usage` today. No pruning job yet; add a retention window
  (or monthly partitioning) when volume warrants. The failure throttle
  keeps the growth rate bounded in the meantime.
- **Retrieval / sync events.** Synchronous paths surface their errors
  inline (409 / response body) and are deliberately excluded — see "Why
  worker events specifically". If a future async retrieval path appears,
  add its `source` to the CHECK vocabulary then.
- **Cross-worker correlation.** Events are independent rows; there's no
  "this `4001` is the same root cause as that `3002`" linking. Out of
  scope until there's a use for it.
